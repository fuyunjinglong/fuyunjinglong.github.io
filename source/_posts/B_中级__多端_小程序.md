# 初级

## 小程序的相关文件类型

**一、定义**

> 它采用了四类核心文件类型来构成一个完整的页面：**`.json`（配置）、`.wxml`（结构）、`.wxss`（样式）和 `.js`（逻辑）**。这种设计遵循了关注点分离的原则，同时便于底层进行编译和安全管控。

**二、 核心文件类型**

**1. `.json` 配置文件**

> - **作用**：用于静态配置，决定页面或整个应用的外在表现和路由。
> - 分类：
>   - **全局配置 (`app.json`)**：配置所有页面路径、窗口全局表现（navigationBarTitleText 等）、底部 TabBar、网络超时时间等。
>   - **页面配置 (如 `index.json`)**：只能配置当前页面的窗口表现，会覆盖全局配置。还可以在此声明引入的第三方组件（`usingComponents`）。
> - **注意**：json 文件不能写注释，且必须是严格的 JSON 格式（键需双引号，不能有多余逗号）。

**2. `.wxml` 模板文件**

> - **作用**：类似于 Web 中的 HTML，负责构建页面的结构。
> - 核心特点：
>   - **标签不同**：不使用传统的 `div`、`span` 等，而是使用小程序内置组件，如 `view`、`text`、`image`、`button` 等。
>   - **指令不同**：使用 `wx:if`、`wx:for` 等指令进行条件渲染和列表渲染，替代了传统的 JS DOM 操作。
>   - **数据绑定**：通过 Mustache 语法（双大括号）进行数据绑定，接收逻辑层 `data` 中的数据。

**3. `.wxss` 样式文件**

> - **作用**：类似于 Web 中的 CSS，负责页面的样式描述。
> - 核心特点：
>   - **新增尺寸单位 `rpx`**：响应式像素，解决了不同屏幕分辨率下的适配问题。小程序底层会自动将 `rpx` 换算成 `px`。
>   - **样式隔离**：提供了组件样式隔离机制，如在自定义组件中可以通过配置 `styleIsolation` 防止样式互相污染。
>   - **全局与局部**：`app.wxss` 为全局样式，页面 `.wxss` 会覆盖全局样式，且只对当前页面生效。

**4. `.js` 逻辑文件**

> - **作用**：处理业务逻辑、网络请求、用户交互响应等。
> - 核心特点：
>   - **生命周期**：通过 `Page()` 或 `Component()` 注册页面/组件时，需配置 `onLoad`、`onShow`、`onReady` 等生命周期函数。
>   - **数据更新**：由于双线程架构，JS 层不能直接操作 DOM，必须通过调用 `this.setData()` 方法，将数据从逻辑层发送到视图层，触发 UI 更新。

实际开发中还会高频使用以下类型：

> 1. `.wxs` (WeiXin Script)：
>    - 小程序特有的脚本语言，**运行在视图层（WebView）中**。
>    - **应用场景**：在 WXML 中处理一些简单的逻辑（如格式化日期、过滤数据），由于不涉及跨线程通信，它在处理高频交互事件（如拖拽、滚动监听）时性能远优于 JS 文件中的函数。
> 2. 自定义组件文件：
>    - 小程序支持将一组文件（json、wxml、wxss、js）封装成一个自定义组件。在页面的 json 文件中通过 `usingComponents` 注册后，即可在 WXML 中像使用内置组件一样使用它。

**三、与传统 Web 前端的对比**

做了很多**约束和增强**

> 1. **结构上**：禁用了 DOM API，强制使用 WXML 的数据绑定和指令，从源头杜绝了 XSS 攻击，并方便底层将其编译为虚拟 DOM。
> 2. **样式上**：引入 `rpx` 适配多端，强化了组件级样式隔离。
> 3. **逻辑上**：严格规范了数据流的单向更新机制（`setData`），牺牲了一部分灵活性，换取了双线程下的安全和可控。

## WXSS 和 CSS

**一、定义**

> WXSS（WeiXin Style Sheets）在语法基础上与传统 Web 的 CSS 保持一致，但为了适配小程序的**双线程架构**、**多端设备屏幕差异**以及**组件化开发体系**，微信团队对 CSS 进行了**扩展和约束**。核心的区别主要体现在四个方面：尺寸单位、样式隔离、选择器限制以及底层编译机制。

**二、核心差异**

**1. 新增了响应式尺寸单位 `rpx`（核心考点）**

> - **传统 CSS**：主要依赖 `px`、`em`、`rem`、`vw/vh`。在进行移动端适配时，通常需要借助 `rem` 或手写媒体查询，依赖开发者手动计算或配置 `flexible.js`。
> - 小程序 WXSS：底层内置了rpx（responsive pixel）。
>   - **原理**：规定任何屏幕的宽度都固定为 `750rpx`。小程序底层在渲染时，会根据当前设备的屏幕宽度自动进行 `rpx` 到 `px` 的换算。
>   - **优势**：开发者无需再关心设备分辨率，只要设计师按照 `750px` 宽度出图，前端直接将设计稿上的 `px` 数值除以 `2`（或者按照 1:1 对应）写为 `rpx` 即可完美自适应。彻底免除了手写适配逻辑的痛苦。

**2. 强大的组件样式隔离机制**

> - **传统 CSS**：全局作用域，样式极易互相污染。为了解决污染，前端界演进出了 BEM 命名规范、CSS Modules、Vue 的 `scoped` 等方案。
> - 小程序 WXSS：原生内置了样式隔离。在自定义组件的Component构造器中，可通过options.styleIsolation配置隔离模式：
>   - `isolated`（默认）：组件内外样式互不影响，最安全。
>   - `apply-shared`：页面 wxss 可以影响组件，但组件不影响页面。
>   - `shared`：双向互相影响。
>   - 这种机制从底层框架级别杜绝了组件间的样式耦合。

**3. 选择器支持的限制（性能考量）**

> - **传统 CSS**：支持所有复杂的选择器，包括 `*` 通配符、属性选择器 `[attr=val]`、各种伪类伪元素等。
> - 小程序 WXSS：为了保证视图层渲染性能，做了大量裁剪。
>   - **不支持通配符 `\*`**：因为通配符会遍历所有节点，在小程序的 WebView 渲染层会引起巨大的性能开销。
>   - 不支持属性选择器，伪类支持也非常有限（仅支持 `::before` 和 `::after`）。
>   - 建议且常用的只有：类选择器、ID 选择器、元素选择器以及后代选择器。

**4. 全局与局部样式的天然划分**

> - **传统 CSS**：通常靠页面入口的引入顺序来区分全局与局部。
> - 小程序 WXSS：在工程结构上天然划分。
>   - `app.wxss`：全局样式，作用于所有页面。
>   - `page.wxss`：页面级样式，只作用于当前页面，且优先级高于全局样式。

**三、 底层编译与运行机制**

> 1. **编译转换**：在代码上传或编译阶段，小程序工具会将 WXSS 编译为纯 CSS。其中，所有的 `rpx` 单位会被动态计算成对应的 `px` 数值（例如在 iPhone 6 上，`1rpx = 0.5px`）。
> 2. **注入机制**：生成的 CSS 最终会被注入到运行视图层（WebView）的 `<style>` 标签中。由于小程序视图层和逻辑层分离，样式的解析和渲染完全在视图线程独立完成，不会阻塞逻辑层的 JS 运算。

**四、实战经验**

> WXSS 本质上是微信团队针对移动端和小程序架构量身定制的“**受限且增强版 CSS**”。它通过 `rpx` 解决了适配痛点，通过 `styleIsolation` 解决了工程化样式污染问题，通过限制选择器保证了渲染性能。
>
> 在实际开发中，我的经验是：**布局尺寸尽量使用 `rpx` 保证流式适配，但字体大小（font-size）和边框（border）通常还是使用 `px`**，防止在大屏设备上字体过大或边框过粗导致视觉变形。同时，严格遵循组件样式隔离，避免使用深层级的后代选择器穿透。

## 生命周期

**一、定义**

> 生命周期主要分为三个层级：**应用级生命周期、页面级生命周期以及组件级生命周期**。它们共同决定了小程序从初始化、前台后台切换、页面加载渲染到销毁的整个运行流程。

**二、核心概念**

**1.App 应用级生命周期（全局唯一）**

定义在 `app.js` 中，主要管理小程序的全局状态和前后台切换：

> - `onLaunch`：初始化完成时触发，**全局只触发一次**。常用于获取用户登录凭证、检查小程序更新、获取设备信息等。
> - `onShow`：小程序启动，或从后台进入前台时触发。常用于重置全局数据、恢复音视频播放等。
> - `onHide`：小程序从前台进入后台时触发。常用于暂停音视频播放、停止定时器、保存当前状态等。
> - `onError`：小程序发生脚本错误或 API 调用失败时触发。常用于全局错误上报和日志收集。

**2.Page 页面级生命周期**

定义在页面的 `.js` 文件中，主要管理页面的加载、渲染和销毁：

> - `onLoad`：页面加载时触发，**一个页面只会调用一次**。常用于获取路由参数（`options`）、发起首次网络请求。
> - `onShow`：页面显示时触发，包括从其他页面返回当前页。常用于刷新页面数据、更新视图状态。
> - `onReady`：页面初次渲染完成时触发。常用于获取节点信息（类似 Vue 的 `mounted`），执行动画操作。
> - `onHide`：页面隐藏/被覆盖时触发。常用于暂停页面级的轮询或动画。
> - `onUnload`：页面卸载时触发（如 `navigateBack` 或 `redirectTo`）。常用于销毁定时器、解绑事件监听、释放内存。

**3.Component 组件级生命周期（扩展深度）**

如果面试官追问组件，可补充：

> - `created`：组件实例进入内存。此时不能调用 `this.setData`，常用于获取自定义属性。
> - `attached`：组件挂载到页面节点。可以开始调用 `this.setData`。
> - `ready`：组件布局完成。
> - `detached`：组件被移除。常用于清理工作。

**三、执行顺序**

在实际开发中，理清它们的执行顺序非常重要。以**小程序冷启动进入首页 A** 为例，执行顺序如下：

> 1. `App.onLaunch` (应用初始化)
> 2. `App.onShow` (应用进入前台)
> 3. `Page A.onLoad` (页面A加载)
> 4. `Page A.onShow` (页面A显示)
> 5. `Page A.onReady` (页面A初次渲染完成)

如果从页面 A `navigateTo` 到页面 B，此时 A 被 B 覆盖，顺序为：

> `Page B.onLoad` -> `Page B.onShow` -> `Page B.onReady` -> `Page A.onHide`

**四、进阶**

1.在面试中，我通常会对比 `onLoad` 和 `onShow`：

> - `onLoad` 只执行一次，适合做一次性初始化操作；
> - `onShow` 每次页面展示都会执行，适合做数据刷新。如果我们在 `onShow` 里发请求，一定要做好节流和防抖，避免频繁请求接口。

2.内存泄漏

> 在 `onLoad` 或 `onShow` 中开启的定时器，必须在 `onUnload` 或 `onHide` 中清理，否则容易导致内存泄漏。

3.异步回调与销毁竞态

> 在 `onLoad` 中发起的异步请求，如果回调时页面已经 `onUnload`（比如用户快速返回），此时调用 `this.setData` 会报错或引发性能问题，建议在回调中判断页面是否已销毁。

4.首页白屏优化

> 不要在 `App.onLaunch` 中放过多耗时的同步逻辑，否则会阻塞 `Page.onLoad` 导致首页白屏过久。

5.用的是 Taro 或 uni-app 等跨端框架

> 在跨端框架中，通常会将小程序的生命周期映射到 React/Vue 的生命周期中，比如 Taro 把 `onLoad` 映射为组件的 `componentWillMount`，把 `onShow` 映射为 `componentDidShow`。



## 页面间传递数据

**一、定义**

> 根据**数据流向（向前传还是向后传）**、**数据量大小**以及**是否需要持久化**来选择最合适的技术方案。常见的传递方式主要分为五种：URL 参数传参、页面栈直接操作、EventChannel 事件通道、全局状态（globalData/Storage）以及状态管理库。

**二、核心传递方式**

**1. URL 参数传参（最基础，正向传递）**

> - **适用场景**：向下一个页面传递少量、非敏感的简单数据。
> - **实现方式**：在 `wx.navigateTo` 的 URL 中拼接 query 参数。目标页面在 `onLoad(options)` 生命周期中接收。
> - **局限性**：只能正向传递，且 URL 长度有限制，无法直接传递复杂对象（需先 `JSON.stringify`，接收后再 `JSON.parse`）。

```js
    // A页面跳转
    wx.navigateTo({ url: '/pages/detail/detail?id=1&name=test' });
    // B页面接收
    onLoad(options) { console.log(options.id, options.name); }
```

**2. 页面栈直接操作（常用，逆向传递）**

> - **适用场景**：从子页面（如详情页、表单填写页）返回上一页，并携带数据回传（如刷新列表）。
> - **实现方式**：通过 `getCurrentPages()` 获取当前页面栈实例，通常取倒数第二个元素即为上一页，然后直接调用上一页的 `setData` 或自定义方法。
> - **局限性**：属于强耦合的写法，如果页面层级发生变动可能会报错；且不符合严谨的数据流单向原则，但在轻量级场景下最实用。

```js
    // B页面返回A页面
    const pages = getCurrentPages();
    const prevPage = pages[pages.length - 2];
    prevPage.setData({ newListData: [...] }); // 直接回写数据
    wx.navigateBack();
```

**3. EventChannel 事件通道（正规，逆向传递）**

> - **适用场景**：同样用于向上一页面传递数据，但比页面栈更规范、解耦更好。
> - **实现方式**：在 `wx.navigateTo` 时会被解析为一个 `EventChannel`，在上一页监听事件，在下一页触发事件。

```js
    // A页面：监听
    wx.navigateTo({
      url: '/pages/detail/detail',
      events: {
        updateData: function(data) { console.log('收到B页数据', data); }
      }
    });
    // B页面：触发
    const eventChannel = this.getOpenerEventChannel();
    eventChannel.emit('updateData', { id: 123 });
```

**4. 全局状态 globalData 与 Storage（跨页面/跨层级传递）**

> - **适用场景**：多层级穿透传递（如 A -> B -> C），或者全局共享状态（如用户信息、主题色）。
> - **globalData**：在 `app.js` 中定义 `globalData`，各页面通过 `getApp().globalData` 读写。适合存内存级临时数据，但无响应式效果，改了数据需手动 `setData` 触发视图更新。
> - **Storage**：通过 `wx.setStorageSync` / `wx.getStorageSync`。适合需要持久化（如用户登录态 Token），容量限制为 10MB。不适合存大量数据或复杂对象，因为序列化耗性能。

**5. 状态管理库（复杂应用必备）**

> - **适用场景**：大型小程序，多页面频繁共享状态（如购物车数据全局同步）。
> - **实现方式**：使用 `mobx-miniprogram` 或 `redux` 结合小程序的 `behaviors` 或 `store` 注入。实现数据响应式，任意页面修改 Store 数据，所有关联页面自动更新。

**三、选型建议**

在实际工程中，我通常会封装一个统一的导航跳转方法，内部集成 URL 参数解析和页面栈的安全获取校验，防止因层级问题导致的报错，提升代码的健壮性。

> 1. **简单的正向传参**，首选 **URL 拼接**。
> 2. **返回上一页回传数据**，轻量级场景用 **`getCurrentPages()`** 直接改数据，如果追求规范解耦则用 **EventChannel**。
> 3. **多页面共享或持久化**，如登录态用 **Storage**，临时全局状态用 **globalData**。
> 4. **重度状态驱动的业务**，引入 **状态管理库** 统一维护。

## bindtap 和 catchtap 的区别

**一、定义**

> `bindtap` 和 `catchtap` 都是小程序中用来绑定点击事件的属性，它们的核心区别在于**对事件冒泡的处理机制不同**：`bindtap` 会触发事件冒泡，而 `catchtap` 会阻止事件冒泡。

**二、最佳实践**

> 1. **避免滥用 catchtap**：不要为了图省事到处用 `catchtap`，这可能会阻止某些全局组件（如弹出层外部点击关闭）的正常冒泡。只在确实需要阻断父子元素事件冲突时使用。
> 2. **弹窗遮罩层场景**：遮罩层和内部弹窗通常都需要绑定点击关闭事件。如果用户点击内部弹窗，不希望遮罩层关闭，此时内部弹窗的 `view` 必须使用 `catchtap` 阻断冒泡，遮罩层用 `bindtap` 触发关闭。

**三、面试**

> Q：既然说到 `data-\*` 传参，如果数据量很大，这种传参方式有什么问题吗？
>
> A:*`data-\*` 传参本质上是将数据挂载到 DOM 节点上，如果数据量极大，会加重渲染层的内存负担。另外，在逻辑层和渲染层通信时，序列化和反序列化的成本也很高。所以对于大数据量传参，通常不建议存在 dataset 里，而是推荐通过公共状态管理（如全局 globalData 或状态库）或者通过路由参数来传递。*

## 下拉刷新

**一、定义**

> 主要有三种方式：**原生页面级配置、程序化 API 触发，以及基于 `scroll-view` 的自定义下拉刷新**。日常开发中最常用的是第一种原生配置，它最轻量且体验最好。

**二、核心方案**

**1.原生页面级配置（最常用，全局/页面级）**

分为两步：配置开关 + 处理生命周期

> - **第一步，开启配置**：在页面的 `.json` 配置文件中添加 `"enablePullDownRefresh": true`（也可以在 `app.json` 的 `window` 选项中全局开启）。
> - **第二步，监听事件**：在页面的 `.js` 文件中重写 `onPullDownRefresh` 生命周期函数。当用户完成下拉手势时，会触发该函数，在这里执行重新拉取数据的逻辑。
> - **第三步，停止动画**：数据请求完成后，**必须**手动调用 `wx.stopPullDownRefresh()` 来收起下拉刷新的动画，否则会一直转圈卡住。

**2.程序化 API 触发（适用于无手势交互的场景）**

> - 通过调用 `wx.startPullDownRefresh()` 可以主动触发下拉刷新动画并触发 `onPullDownRefresh` 回调。
> - **应用场景**：常用于页面首次进入时的骨架屏加载，或者在网络超时后，用户点击“重试”按钮时主动触发刷新。

**3.基于 `scroll-view` 的自定义下拉刷新（适用于局部或特殊 UI 需求）**

> - 如果页面是局部滚动（如嵌套 swiper），或者设计师要求一套非常炫酷的自定义下拉动画（比如一个小球弹跳），原生下拉刷新无法满足。
> - **实现方式**：使用 `<scroll-view>` 组件，开启 `refresher-enabled="{{true}}"` 属性，监听 `bindrefresherrefresh` 事件，并通过 `refresher-triggered` 控制动画关闭状态。这种方式可以完全自定义下拉区域的 UI。

**三、进阶**

> 1. **忘记停止动画**：这是新手常犯的错误，如果请求是异步的，没有在 `.finally()` 或回调中调用 `wx.stopPullDownRefresh()`，下拉动画会一直存在。
> 2. **样式不显示问题**：有时开启了 `enablePullDownRefresh` 但看不到三个点点的动画，通常是因为背景色和动画颜色冲突。需要在 json 中配置 `"backgroundTextStyle": "dark"` 或 `"light"` 来适配背景。
> 3. **局部滚动冲突**：如果页面高度超出一屏且使用的是**局部滚动**布局，原生页面级下拉刷新会失效。此时必须使用 `scroll-view` 的 `refresher-enabled` 方案，而不能用页面级的下拉刷新。
> 4. **防抖与节流**：避免用户连续疯狂下拉导致发起多次重复请求，可以在请求前加一个 `isLoading` 锁。
> 5. 项目使用的是 **Taro 或 uni-app**，底层会将小程序的 `onPullDownRefresh` 映射为 React 的 `usePullDownRefresh` Hook 或 Vue 的页面生命周期钩子，但底层调用的依然是上述小程序原生能力。
> 6. 如果在首页有一个固定的导航栏，下拉刷新时导航栏也跟着一起下拉了怎么办？“这种场景下原生页面级下拉刷新难以处理局部分离。我会改用 `scroll-view` 将导航栏放在 scroll-view 外部，列表放在内部，通过 `refresher-enabled` 实现仅列表区域的局部下拉刷新，从而实现导航栏固定的效果。”

## 自定义组件样式隔离

**一、定义**

> 自定义组件的样式隔离是通过在 `Component` 构造器的 `options` 配置中设置 `styleIsolation` 属性来实现的。它主要提供了 **`isolated`、`apply-shared`、`shared`** 三种隔离模式，用来控制组件内外样式相互影响的范围。

**二、三种隔离模式**

> - `isolated`（默认：完全隔离）
>   - **特性**：组件内外的样式互不影响。页面样式不会影响组件内部，组件内部样式也不会影响外部页面。
>   - **表现**：只有组件中写在 `addGlobalClass: true`（旧基础库的写法）或者通过 `externalClasses` 外部样式类传入的样式才能生效。
> - `apply-shared`（单向共享：页面影响组件）
>   - **特性**：页面（`Page`）的 `wxss` 样式会**影响到**自定义组件内部，但组件内部的样式**不会影响**到外部页面。
>   - **应用场景**：这是日常业务开发中最常用的模式。比如页面定义了主题色（`.primary-color`），希望直接在自定义组件的按钮上也能使用该类名，就可以开启此模式。
> - `shared`（双向共享：互相影响）
>   - **特性**：页面样式会影响组件，组件样式也会影响页面（甚至同一页面中其他配置为 `shared` 或 `apply-shared` 的组件）。
>   - **应用场景**：极少使用，通常用于设计极其基础的全局基础组件（如UI库的根容器），需要组件内部定义的样式能反向污染页面。**一般不建议轻易使用，容易引发样式冲突**。

**三、外部样式类与样式透传**

除了配置隔离模式，小程序还提供了更精确的样式穿透控制：

> 1. **外部样式类（`externalClasses`）**：组件内部声明 `externalClasses: ['my-class']`，在组件节点上传入 `<comp my-class="theme-red">`，这样可以在不打破样式隔离的情况下，让外部精确控制组件内部某个节点的样式。
> 2. **页面样式隔离（页面配置）**：除了组件，`Page` 也可以在 `.json` 中配置 `styleIsolation`，控制页面样式是否隔离。

**四、进阶**

> **（1）为什么默认要 `isolated`？**
> 小程序组件化的核心诉求就是**高内聚低耦合**。如果默认不隔离，由于小程序的 WXSS 最终都会合并到同一个渲染层 Webview 中执行，全局样式很容易意外污染组件内部，导致 UI 错乱。
>
> **（2）踩坑点：标签选择器穿透**
> 有一个大坑是：即使开启了 `isolated` 完全隔离模式，组件内部仍然可以使用**标签选择器**（如 `view { color: red }`）。由于小程序底层的实现机制，标签选择器是**无法被隔离**的，它会污染到整个页面的所有 `view` 标签。
> **最佳实践**：在组件内部编写样式时，**绝对不要使用标签选择器**，必须使用 class 选择器（`.container`），否则会引起诡异的样式污染问题。
>
> **（3）跨端框架的差异**
> 如果使用 Taro 或 uni-app，由于它们底层将 React/Vue 的样式编译处理过，通常默认会启用类似 CSS Modules 的局部作用域，开发者较少直接感知小程序原生的 `styleIsolation`，但底层原理依然受此机制约束。
>
> (4)既然 `apply-shared` 可以让页面样式影响组件，那如果我只想让页面传入一个特定的样式类名，不想暴露组件内部结构，用哪种方案更好？
>
> *我会优先使用 `externalClasses` 外部样式类。因为 `apply-shared` 是一种粗粒度的单向敞开，页面中所有符合选择器的样式都会塞进去；而 `externalClasses` 是一种细粒度的契约，组件内部明确声明哪个节点需要外部样式，这样更加安全可控，符合黑盒组件的设计原则。*

## 微信支付业务流程

**一、定义**

> 核心流程包括**“三端协同”**：小程序前端负责发起支付和感知用户操作，业务后端负责创建订单和生成预支付参数，微信服务器负责统一下单和资金扣减。整个流程的关键在于保证订单的闭环和安全校验。

> 用户点击支付` ➔ `前端请求后端` ➔ `后端请求微信下单` ➔ `微信返回 prepay_id` ➔ `后端签名返回前端` ➔ `前端调 wx.requestPayment` ➔ `用户支付` ➔ `微信异步通知后端` ➔ `前端轮询后端状态

**二、核心流程**

以标准的 JSAPI 支付（小程序支付）为例，分为以下几步：

**第一阶段：统一下单与参数生成（前端 -> 后端 -> 微信）**

> 1. **前端发起请求**：用户在小程序点击“去支付”，前端将商品信息（如商品 ID、购买数量）传给业务后端。
> 2. **后端创建订单**：业务后端校验库存、金额，在本地数据库生成一条未支付状态的订单记录（获取业务订单号 `out_trade_no`）。
> 3. **后端调用微信 API**：业务后端携带订单号、金额、`openid` 等参数，调用微信服务器的**【统一下单接口】**。
> 4. **微信返回预支付参数**：微信服务器校验通过后，返回预支付交易会话标识 `prepay_id`。后端使用 `prepay_id` 加上时间戳、随机字符串等，按微信规则生成**前端支付签名 `paySign`**，并将这些参数返回给小程序前端。

**第二阶段：前端唤起支付（前端 -> 微信）**

> 5. **前端唤起支付弹窗**：前端收到后端返回的参数后，调用小程序原生 API `wx.requestPayment`，传入 `timeStamp`、`nonceStr`、`package`（`prepay_id`）、`signType`、`paySign`。
> 6. **用户输入密码支付**：此时微信弹出支付界面，用户确认指纹或密码。前端进入 `wx.requestPayment` 的回调等待状态

**第三阶段：支付结果闭环（微信 -> 后端 -> 前端）**

> 7. **微信异步回调后端**：用户支付成功后，微信服务器会**异步**向业务后端的回调接口发送支付结果通知。后端需验证签名，确认无误后，将本地订单状态更新为“已支付”，并给微信返回成功应答（防重入）。
> 8. **前端获取结果展示**：前端通过 `wx.requestPayment` 的 `success` 或 `fail` 回调获取同步结果。**注意：前端的成功回调不能作为最终扣款成功的唯一依据**，必须结合后端状态。前端通常在 `success` 后轮询后端接口，确认订单真正变为“已支付”后，再跳转到“支付成功”页面。

**三、进阶**

> 1. **以前端同步回调为准（致命坑）**：`wx.requestPayment` 的 `success` 回调只代表“用户输入密码且微信客户端返回成功”，可能存在网络延迟导致后端还没收到微信异步通知。**绝对不能在前端回调里直接判定业务成功**，必须轮询后端接口确认。
> 2. **后端回调的幂等性**：微信的异步通知可能会重复发送（比如后端没及时回复 ACK）。业务后端的回调接口必须做好**幂等性处理**，防止重复发货或重复更新状态。
> 3. **金额单位防坑**：微信支付的所有金额单位都是**分**，而前端展示和后端业务计算经常用**元**，在调用统一下单接口时必须做好转换，且最好用整数分，避免浮点数精度问题。
> 4. **体验优化**：如果用户支付中途退出（`fail` 回调），前端不要直接跳转失败页，而是提示“支付未完成，可重新支付”，并保留订单状态，方便用户再次拉起支付。



## 自定义 navigationBar

**一、定义**

> 核心思路是：**关闭原生导航栏 -> 动态获取系统状态栏和胶囊按钮的尺寸 -> 计算出自定义导航栏的真实高度 -> 编写自定义组件进行渲染并占位**。

整个过程中最大的难点在于**多机型（如刘海屏、Android 各种屏幕）的尺寸适配**，尤其是如何与右上角固定的原生胶囊按钮在视觉上保持对齐。

**二、核心步骤**

**1. 开启自定义导航栏配置**

在页面的 `.json` 配置文件中（或 `app.json` 全局配置），将 `navigationStyle` 设置为 `custom`。

```json
{
  "navigationStyle": "custom"
}
```

*注：设置后，原生顶部导航栏会消失，但右上角胶囊按钮（返回、首页、关闭）依然会原生渲染在屏幕右上角。*

**2. 获取系统尺寸数据（核心难点）**

为了适配所有机型，必须在 JS 中动态获取两个关键数据：

> - **状态栏高度（StatusBarHeight）**：通过 `wx.getWindowInfo()` 或 `wx.getSystemInfoSync()` 获取 `statusBarHeight`。这部分不同机型差异极大（如 iPhone X 以上的刘海屏较大）。
> - **胶囊按钮尺寸（MenuButton）**：通过 `wx.getMenuButtonBoundingClientRect()` 获取胶囊按钮的 `top`、`bottom`、`height`、`width`。

**3. 计算导航栏总高度**

获取到数据后，进行关键计算。导航栏的总高度不能写死，通常的计算逻辑是：

> - **导航栏内容区高度** = (胶囊按钮上边距 - 状态栏高度) * 2 + 胶囊按钮高度
> - **导航栏总高度** = 状态栏高度 + 导航栏内容区高度
>   *说明：这样计算能保证我们的标题/Logo 与右上角胶囊按钮在垂直方向上绝对居中对齐。*

**4. 布局实现与占位**

在 WXML 和 WXSS 中构建结构：

> - 通常使用 `fixed` 定位将自定义导航栏固定在顶部。
> - **关键点**：由于使用了 `fixed` 脱离文档流，页面下方内容会被导航栏遮挡。必须加一个与导航栏高度相等的占位元素（如空的 `view`），或者给页面容器设置 `padding-top` 为导航栏总高度。

**三、进阶**

有几个容易踩坑的细节：

**1.生命周期时序问题**

> `wx.getMenuButtonBoundingClientRect()` 有时在 `onLoad` 中获取会存在时延导致获取不到。为了确保数据准确，我通常会在 `onReady` 或使用 `setTimeout` 中稍作延迟获取，或者将其封装为全局方法在 `App.js` 的 `onLaunch` 中提前异步获取并缓存。

**2.下拉刷新的适配问题**

> 开启自定义导航栏后，原生的下拉刷新起点会发生变化（可能在屏幕最顶端）。可以通过配置 `pageBackgroundColorTop` 或者使用自定义的滚动容器配合 `scroll-view` 的 `refresher` 属性来实现完全自定义的下拉刷新效果。

**3.返回首页与多端兼容**

> - 当页面是第一个页面时，胶囊按钮左侧没有“<”返回箭头，需要在自定义导航栏左侧添加“返回首页”的逻辑（`wx.switchTab` 或 `wx.reLaunch`）。
> - 如果是开发支付宝/抖音小程序，他们的 API 不同，如果是跨端框架（如 uni-app/Taro），建议使用框架封装的 `getMenuButtonBoundingClientRect` 保证一致性。

**四、实战经验**

> 综上所述，自定义 navigationBar 的本质是**放弃原生 UI，通过 API 计算做绝对定位的还原与增强**。
>
> 在工程化实践中，我不会在每个页面重复写这段逻辑。我会将其抽离为一个**全局的 `custom-navbar` 自定义组件**。在组件内部处理所有的尺寸计算、返回按钮逻辑、背景色渐变逻辑，并通过 `properties` 暴露 `title`、`bgColor` 等属性供各个页面复用。这样既保证了 UI 的一致性，又极大地降低了页面的维护成本。

## 双向绑定在小程序与Vue的区别

**一、定义**

> **Vue 是基于数据劫持和单线程的响应式系统，而小程序是基于跨线程通信和语法糖封装的双线程模型**。

**二、核心区别**

| 维度             | Vue 双向绑定                 | 小程序双向绑定                |
| :--------------- | :--------------------------- | :---------------------------- |
| **核心原理**     | 数据劫持 + 依赖收集          | 事件回调 + `setData` (语法糖) |
| **线程模型**     | 单线程 (同进程)              | 双线程 (跨进程通信)           |
| **数据驱动方式** | 数据改变自动触发 DOM 更新    | 必须通过 `setData` 跨线程驱动 |
| **灵活性**       | 高（支持修饰符、计算属性等） | 低（受限，无修饰符）          |
| **性能瓶颈**     | DOM Diff 与重绘              | 跨线程通信开销与序列化        |

**1. 底层实现机制不同**

> - **Vue 的实现**：基于**数据劫持 + 发布订阅模式**。Vue 2 利用 `Object.defineProperty`，Vue 3 利用 `Proxy` 拦截数据的读写。当用户修改输入框时，触发 input 事件改变数据，数据的 Setter 拦截到变化后，通知依赖该数据的 Watcher，进而触发虚拟 DOM 的 Diff 和真实 DOM 的更新。整个过程在同一进程内完成。
> - **小程序的实现**：本质是**单向数据流 + 事件回调的语法糖**。小程序底层并没有对 `data` 对象进行数据劫持。当使用 `model:value` 时，小程序底层帮我们做了两件事：一是将数据渲染到视图；二是监听输入事件，自动调用 `this.setData` 将新值传回逻辑层。数据变化的触发力来自 `setData`。

**2. 线程模型与通信开销不同**

> - **Vue（单线程）**：逻辑层和视图层都在浏览器的 JS 引擎和渲染引擎中，数据更新是在同一内存空间中完成的，通信开销极小，速度极快。
> - **小程序（双线程）**：逻辑层运行在 JsCore/V8 中，视图层运行在 WebView 中。双向绑定的数据发生变化时，逻辑层必须将数据**序列化为字符串**，通过 Native 层的 JSBridge **跨线程**传递给视图层，视图层再进行渲染。这就带来了不可忽视的通信开销。

**3. 语法灵活性与限制不同**

> - **Vue 的 `v-model`**：极其灵活。可以绑定计算属性、支持修饰符（如 `.lazy`、`.trim`、`.number`），可以绑定动态组件，甚至能在自定义指令中深度定制双向绑定逻辑。
> - **小程序的 `model:value`**：相对受限。它是语法糖，不支持修饰符；虽然支持多级路径绑定（如 `model:value="{{obj.a}}"`），但不支持复杂的表达式或函数过滤；在自定义组件上使用时，子组件必须主动触发 `bind:update:propName` 事件才能完成双向绑定。

**4. 性能瓶颈与优化方向不同**

> - **Vue**：性能瓶颈主要在于大列表的虚拟 DOM Diff 计算和浏览器的重排重绘。优化方向是 `v-if`/`v-show` 选择、`key` 的设置、组件缓存等。
> - **小程序**：性能瓶颈主要在于**频繁的跨线程通信**。在输入框高频输入时，如果每次输入都触发 `setData`（即使使用了 `model:value`），会导致 JSBridge 线程通信堵塞，引起输入卡顿。优化方向是做防抖、使用运行在视图层的 WXS 处理高频事件，或只 `setData` 变化的局部数据。

**三、进阶**

> 综上所述，Vue 的双向绑定是一种**底层级别的响应式设计**，旨在消除开发者对 DOM 的操作；而小程序的双向绑定是对**双线程单向数据流的一种上层封装**。
>
> 小程序之所以不直接照搬 Vue 的数据劫持，是因为双线程架构下逻辑层根本没有 DOM 可以直接操作，劫持数据也无法直接通知到另一个线程的 WebView 去更新 UI，必须老老实实走 `setData` 桥接。这种设计虽然带来了语法上的便利，但也要求我们在开发高频交互场景时，必须清楚底层的跨线程代价，不能盲目依赖双向绑定，而应结合防抖或 WXS 技术进行优化。



# 高级

## 小程序的优劣势

**一、定义**

> 核心优势在于**“依托超级 App 生态、获客成本低、体验接近原生”**；而它的劣势主要受限于**“双线程架构带来的性能瓶颈、包体积限制以及受制于平台规则”**。它本质上是一种在 Web 和原生 App 之间的折中态产物。

**二、优势**

**1.用户体验好，触达成本低（获客优势）**

> - **免下载、免安装**：用户即点即用，用完即走，使用门槛极低，极大提高了转化率。
> - **社交裂变容易**：依托微信等超级 App 的社交关系链，通过分享卡片、群聊等极易实现裂变式传播，获客成本远低于原生 App。

**2.开发与维护成本低（研发优势）**

> - **跨平台能力**：一套代码可以同时在 iOS 和 Android 两端运行，甚至通过跨端框架（如 Taro、uni-app）还能兼容 H5 和其他小程序。
> - **发版速度快**：支持热更新，无需走冗长的 App Store / Android 应用市场审核流程（仅需平台方小程序后台审核），修复 Bug 和上线新功能极快。

**3.原生能力强（技术优势）**

> - 相比普通 Web 页面受限于浏览器沙盒，小程序可以通过原生桥调用大量系统级能力（如蓝牙、定位、文件系统、生物认证等），体验更接近原生 App。

**三、劣势**

**1.性能瓶颈与架构限制（技术劣势）**

> - **双线程通信开销**：逻辑层（JS Core）和渲染层（WebView）分离，`setData` 跨线程通信耗时，导致处理高频动画、长列表滚动等复杂交互时性能不如原生 App 甚至部分优化的 H5。
> - **包体积限制**：为了保证秒开体验，小程序对代码包体积有严格限制（主包通常 2M，总包通常 20M+），无法承载过重的大型业务。

**2.生态封闭与规则限制（业务劣势）**

> - **受制于宿主平台**：小程序的流量入口、审核规则、支付体系（如必须用微信支付）完全受控于宿主 App，存在“卡脖子”风险。
> - **多端差异化**：如果使用原生语法开发微信小程序，难以直接迁移到支付宝、抖音等平台；即使使用 Taro 等跨端框架，也需处理多端 API 差异的坑。

**3.用户留存率低（运营劣势）**

> - 由于“用完即走”的属性，用户往往通过群聊或扫码进入，用完即退，缺乏常驻桌面的入口，导致用户召回成本高、留存率通常低于原生 App。

**四、场景选型**

通常会对比三种方案：

> 1. **原生 App**：适合**重度交互、高频使用、需极高性能或沉淀核心资产**的业务（如大型游戏、短视频主端）。
> 2. **H5**：适合**强外部传播、弱原生能力依赖、对加载速度要求不极端**的营销活动页。
> 3. **小程序**：适合**需要社交裂变、用到一定原生能力、追求比 H5 更好体验的轻量级服务**（如电商购物、点餐、出行服务）。

## 提升小程序应用速度

**一、定义**

> 主要围绕**“代码包更小、首屏渲染更早、网络请求更快、线程通信更少”**四个核心维度展开

**二、核心方法**

**1.体积与加载优化（减小主包，加快下载）**

> - **分包加载（`subPackages`）**：将非首屏页面放入分包，按需加载。主包体积越小，冷启动下载越快。
> - **分包预下载（`preloadRule`）**：在用户进入某分包页面*之前*，利用空闲时间提前下载分包，实现“无感加载”。
> - **按需注入（`lazyCodeLoading`）**：在 `app.json` 中配置 `"lazyCodeLoading": "requiredComponents"`，未使用的组件代码不注入，大幅减少启动耗时。

**2.首屏渲染优化（减少白屏时间）**

> - **初始渲染缓存（`initialRenderingCache`）**：在页面或组件配置中开启。下次启动时，直接展示上次的缓存 UI，同步发起请求更新，有效消除冷启动白屏。
> - **骨架屏**：在数据未到达前展示页面骨架，提升用户体感速度。
> - **避免 `onLoad` 同步阻塞**：`onLoad` 中只做必要逻辑，复杂逻辑延后到 `onReady` 或通过 `setTimeout` 异步执行，不阻塞渲染层

**3.网络请求优化（提前与并发）**

> - **数据预拉取（`prefetch`） / 周期性更新**：利用底层能力，在小程序冷启动时，框架发起请求的同时，底层提前拉取首屏业务数据，减少等待时间。
> - **合理使用缓存**：将不常变更的首屏数据存入 `Storage`，先渲染缓存数据，再异步请求最新数据覆盖（类似 Vue 的 SSR 思想）。

**4.渲染与通信优化（双线程模型特性）**

> - **精简 setData**：小程序逻辑层与渲染层分离，`setData` 是跨线程通信。最佳实践是：合并多次 `setData` 为一次；只传递变化的字段（如 `this.setData({'list[0].name': 'abc'})`），避免全量更新。
> - **使用 pureDataPattern**：将仅用于逻辑处理、不需要渲染的数据设为纯数据字段，避免无意义的 `setData` 传输。

**三、场景化应用：冷启动首屏流程**

在实际开发中，我会将这些方法组合使用。以首页冷启动为例：

> 1. 用户点击小程序，底层开始下载**精简后的主包**（体积优化）。
> 2. 同时框架底层发起**预拉取请求**获取首屏数据（网络优化）。
> 3. 页面加载，立即展示**初始渲染缓存 UI** 和骨架屏（渲染优化）。
> 4. 预拉取数据返回后，通过**合并的 `setData`** 更新视图，完成首屏可见。

**四、底层原理**

> 这些优化手段的本质是为了应对小程序的**双线程模型**（逻辑层 JS Core 与渲染层 Webview）。启动慢的原因通常是主包下载耗时、JS 代码注入解析耗时，以及跨线程通信耗时。比如优化 `setData`，就是为了减少数据序列化、跨线程传输和 DOM Diff 的开销；开启按需注入，就是为了减少启动时解析无用 JS 的 CPU 开销。
>
> setData原理：*setData 会将数据从 JS Core 序列化为字符串，通过 JSBridge 传给 Webview，Webview 反序列化后进行 DOM Diff 再渲染，所以高频或大数据量的 setData 会引发性能瓶颈。*

**五、进阶**

> 1. **初始缓存数据陈旧问题**：使用初始渲染缓存时，如果业务数据变化快，用户会先看到旧数据再闪烁变新数据。最佳实践是在占位图或某些不敏感的 UI 上使用，或者在请求返回后做好过渡动画。
> 2. **过度预下载**：分包预下载如果配置过多，会占用网络带宽和内存，反而拖慢主包的加载，需要根据用户实际路径合理规划。
> 3. **基础库版本兼容**：如 `lazyCodeLoading` 需要基础库 2.11.1 及以上，使用时需做好版本降级或兼容提示。

## 小程序的原理

**一、定义**

> 小程序的运行原理，其核心设计思想是**双线程架构**。小程序将**视图层**和**逻辑层**进行了分离，两者在不同的线程中运行，通过微信客户端（Native）作为桥接进行通信。

**二、核心架构**

**1. 视图层（View Layer）**

> - **运行环境**：由 WebView 负责渲染。如果有多个页面，会使用多个 WebView 实例。
> - **主要职责**：解析 WXML、WXSS 进行 DOM 树的构建和页面渲染。
> - **特点**：视图层只能负责纯粹的 UI 展示，不能直接调用业务逻辑数据，必须等待逻辑层通过 `setData` 传递过来。

**2. 逻辑层（Logic Layer）**

> - **运行环境**：在 JsCore（iOS）或 V8（Android）中运行，运行环境由原生提供，**没有浏览器对象模型（没有 BOM/DOM API）**。
> - **主要职责**：执行 JS 业务逻辑、处理网络请求、数据处理等。
> - **特点**：由于隔离了 DOM API，逻辑层无法直接操作 UI，这就强制开发者不能通过 JS 操作节点去改变视图。

**3. 原生层（Native Layer）**

> - **职责**：作为视图层和逻辑层之间的**通信桥梁**，同时提供底层的 API 能力（如定位、摄像头、文件系统等）。
> - **机制**逻辑层和视图层的通信，必须通过 Native 层的 JSBridge 进行转发，**不允许直接跨线程通信**。

**三、通信与渲染机制**

主要分为首次渲染和更新渲染：

**1.首次渲染**

> - 逻辑层通过 `App` 和 `Page` 的生命周期获取初始数据。
> - 逻辑层将初始数据通过 `JSBridge` 传递给视图层。
> - 视图层结合 WXML 和数据生成虚拟 DOM，进而转换为真实 DOM 进行首次渲染。

**2.数据更新（`setData` 机制）**

> - 开发者在逻辑层调用 `this.setData`。
> - 逻辑层将 `data` 与原 `data` 进行 Diff 对比，将**变化的部分数据**序列化为字符串。
> - 通过 `JSBridge` 跨线程将数据传递给视图层。
> - 视图层接收到数据后，结合虚拟 DOM 进行局部更新，重新渲染对应的组件。
> - *注：由于通信需要跨线程且涉及序列化，所以 `setData` 传递大量数据或频繁调用会导致性能瓶颈。*

**四、设计初衷与优势**

小程序之所以放弃传统的 Web 单线程模型，采用双线程架构，主要出于以下考量：

> 1. **安全管控（核心原因）**：传统 Web 中，开发者可以使用 DOM API 动态生成 script 标签、执行外部脚本，存在安全隐患。小程序剥离了 DOM/BOM API，意味着开发者无法随意操作 DOM，所有页面的结构必须经过 WXML 编译，有效防止了 XSS 攻击和恶意跳转，方便微信统一管控。
> 2. **性能体验**：逻辑层不阻塞视图层。在 Web 中，如果 JS 执行耗时任务会导致页面卡顿（白屏）。双线程模型下，JS 的计算和 UI 的渲染互不干扰，保证了页面滚动的流畅度。
> 3. **多端一致性**：通过中间的 Native 桥接和一套自定义的 WXML/WXSS 编译机制，抹平了不同平台（iOS/Android/开发者工具）的浏览器内核差异，保证渲染一致性。
