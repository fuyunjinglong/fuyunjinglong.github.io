# 定义

> 全链路监控 SDK = 用最轻的代价、最不侵入业务的方式，把用户侧的"黑盒"变成可回放、可归因的数据流，再通过网关削峰、流批一体计算和智能告警，把孤立事件还原成完整故事——设计上永远在"采得多"与"跑得快"、"看得全"与"花得少"之间做工程取舍。

**全链路监控是一套贯穿"数据采集 → 处理 → 上报 → 服务端分析 → 可视化告警"的端到端可观测体系，其 SDK 是嵌在用户浏览器/终端侧的轻量采集器，负责在不影响业务的前提下捕获错误、性能、行为、接口等一切可观测数据。**

 它与传统"报错收集"的本质区别在于：不仅要回答"发生了什么错误"，还要能还原"用户做了什么、页面处于什么状态、链路哪个环节出了问题"——即从孤立日志走向可回放、可归因的完整场景。

之所以叫"全链路"，是因为它打通了三段链路：**用户行为链路**（点击 → 路由 → 接口 → 渲染）、**请求链路**（前端 → 网关 → 后端服务，通过 Trace ID 串联前后端 APM）、**指标链路**（性能数据与版本发布、设备、地域交叉分析）。前端 SDK 是整条链路的起点和最不可控的一环，因此设计难度最高。

# 整体架构

一个可落地的监控体系通常分四层，SDK 只承担第一层职责

```js
[数据采集层 SDK] → [数据转发层 Gateway] → [存储与计算层] → [可视化与应用层]
```

| 层级                  | 职责                                             | 典型技术选型                                                 |
| --------------------- | ------------------------------------------------ | ------------------------------------------------------------ |
| **采集层（SDK）**     | 端侧无侵入采集、初步过滤聚合、加密压缩、批量上报 | PerformanceObserver、MutationObserver、rrweb、劫持 fetch/XHR |
| **转发层（Gateway）** | 鉴权、协议转换、流量削峰、服务端二次过滤         | Node.js / Go 网关 → Kafka                                    |
| **存储计算层**        | 实时告警 + 离线分析                              | ELK / 时序数据库（实时）；ClickHouse / Hive（离线）          |
| **应用层**            | 看板、告警、Sourcemap 还原、录屏回放             | Grafana / 自建平台 + 告警推送（钉钉/飞书）                   |

网关层的价值常被低估：它把"SDK 直连业务库"解耦成"SDK → 网关 → 队列"，从而支撑大促期间每秒百万级写入的削峰与弹性扩容。

# SDK 核心设计：三大模块

**1.数据采集层**

采集范围按"错误 → 性能 → 行为 → 接口 → 个性化"五大类组织：

| 监控类型       | 采集内容                              | 关键 API / 手段                                              |
| -------------- | ------------------------------------- | ------------------------------------------------------------ |
| **JS 错误**    | 同步错误、语法错误                    | `window.onerror`（跨域脚本需 `crossorigin="anonymous"` + CORS）baidu.com |
| **异步错误**   | Promise 未捕获异常                    | `unhandledrejection` 监听                                    |
| **资源错误**   | 图片/CSS/JS 404                       | `addEventListener('error', true)` 捕获阶段                   |
| **框架错误**   | React/Vue 组件渲染异常                | ErrorBoundary / `app.config.errorHandler`                    |
| **接口错误**   | 请求状态码、耗时、错误类型            | 重写 `XMLHttpRequest` 与 `fetch`，注入 Trace ID              |
| **性能指标**   | LCP / INP / CLS / FCP / TTFB / 长任务 | `PerformanceObserver` + `PerformanceNavigationTiming`mianshidashi.cn |
| **用户行为**   | 点击、输入、路由切换、PV/UV           | 事件委托 + 路由钩子，构建行为栈                              |
| **白屏检测**   | 关键容器是否有内容                    | 采样 DOM 节点 + MutationObserver 判断                        |
| **页面录屏**   | 报错前 N 秒用户操作回放               | rrweb（配合 `maskAllInputs` 脱敏）github.org                 |
| **自定义指标** | 业务关键路径（登录耗时、下单耗时）    | `performance.mark()` + `measure()`                           |

**错误数据结构**要做到可定位，而不只是 message——需包含：错误类型/消息/堆栈/文件行列、页面 URL 与路由、设备与浏览器、网络状态、用户匿名 ID、会话 ID、版本号、构建标识、**报错前最近 N 步行为栈**。生产环境压缩代码需配合 **Sourcemap 上传到内部服务还原源码**（不对外暴露）

**2.数据处理层**

上报前的端侧预处理，是 SDK 的性能护城河：

| 处理手段     | 目的                                                         |
| ------------ | ------------------------------------------------------------ |
| **过滤**     | 白名单排除测试环境、黑名单屏蔽已知噪声（如浏览器插件报错）   |
| **去重聚合** | 按错误指纹（类型 + 归一化堆栈 + 文件 + 函数名）计算哈希，10 万条原始错误合并为几百个问题实例studygolang.com |
| **脱敏**     | 输入内容、手机号、Token 等敏感字段脱敏，满足隐私合规         |
| **数据增强** | 补充设备指纹、网络类型、地理位置等上下文                     |
| **采样**     | 关键路径错误 100% 采集，性能/行为数据按比例采样（详见第四节） |
| **压缩**     | LZ-String / gzip / 自定义二进制协议，JSON 压缩率可达 60%baidu.com |

**3. 数据上报层**

上报策略直接决定数据完整性与对业务的干扰程度：

| 策略                    | 说明                                                         |
| ----------------------- | ------------------------------------------------------------ |
| **优先级分级**          | 致命错误（白屏/崩溃）→ 即时上报；性能/行为数据 → 批量上报    |
| **传输方式**            | 首选 `navigator.sendBeacon`（异步、unload 时仍可发送、可被合并）；降级 `fetch(url, { keepalive: true })`；`<img>` 打点作兜底 |
| **批量触发**            | 按时间间隔（如 5s）或数据量阈值（如 10KB）触发baidu.com      |
| **失败重试 + 离线缓存** | 上报失败先落 IndexedDB / 本地存储，下次启动恢复上传。美团 Logan 的实践显示，仅页面关闭导致的日志丢失就占 1%，落盘机制可显著提升完整率meituan.com |
| **队列管理**            | 弱网/堆积时按数据价值丢弃低优先级请求，防止内存持续上涨meituan.com |
| **跨端统一协议**        | Web / 小程序 / App / Node 共用一套数据协议，核心逻辑复用、平台层单独适配meituan.com |

# 服务端处理与可视化

数据到达后端后的闭环

> 1. **实时链路**：Gateway → Kafka → Flink/ES → 实时告警（错误率突增、LCP 超标、接口失败率异常）
> 2. **离线链路**：ClickHouse 多维交叉分析，按页面/设备/版本/地域/网络下钻
> 3. **告警策略**：固定阈值 + 同比环比 + 突增检测 + 分级通知（P0 电话、P1 群消息）
> 4. **问题还原三件套**：Sourcemap 定位源码 + rrweb 录屏回放 + 行为栈列表——解决"bug 复现不出来"的核心痛点tencent.com
> 5. **指标基线**：用历史数据建立动态基线，基于趋势而非固定阈值告警，降低误报

# 设计难点与取舍

SDK 设计的本质是在多重矛盾中找平衡：

| 矛盾                         | 取舍策略                                                     |
| ---------------------------- | ------------------------------------------------------------ |
| **无侵入 vs 采集完整度**     | 通过代理重写原生方法（fetch/XHR）+ 原生观测 API（PerformanceObserver/MutationObserver）实现无感采集；框架错误通过官方钩子（ErrorBoundary、errorHandler）而非侵入业务代码 |
| **数据量 vs 完整性**         | 端侧初步聚合 + 差异化采样：错误 100%、性能按 P75 关键页面 10-20%、行为埋点按需；大促时动态降采样（如从 10% 降到 1%）studygolang.com |
| **采集丰富 vs SDK 自身开销** | SDK 体积控制在 10KB 量级；插件化架构让核心保持轻量，按需加载功能模块github.org；初始化异步拉取远程配置（采样率、开关、黑名单），支持热更新与灰度 |
| **SDK 不能成为事故源**       | 所有采集逻辑包 try/catch，**采集失败绝不能影响业务运行**；加密存储避免日志泄漏（如 Logan 用 ECDH + AES）meituan.com |
| **实时性 vs 准确性**         | 看板用准实时数据，精确归因交给离线批算；性能指标看 P75/P95 而非平均值，因为少数慢用户才代表真实体验问题mianshidashi.cn |
| **隐私合规**                 | 用户标识匿名化、输入内容脱敏、埋点字段白名单管控、sourcemap 不外泄 |

# 落地路径建议

> - **小团队**：直接接入 Sentry（含 React/Vue 集成、BrowserTracing、Sourcemap 上传），配合 `web-vitals` 库上报核心指标。
> - **中大型团队**：自研价值在于——统一公司多个 SDK（监控/埋点/录屏）、错误与埋点联动获得更细的行为栈、支持自定义指标（长任务、内存、缓存命中率）。
> - **演进顺序**：先做错误监控（最痛）→ 再加性能与 Web Vitals → 再补行为栈与录屏 → 最后打通前后端 Trace ID 实现真"全链路"（接入 OpenTelemetry 上下文传播）。
> - **闭环标准**：一套监控体系是否合格，看它能否回答三个问题——**出了什么问题、影响了多少用户、如何快速定位和恢复**
