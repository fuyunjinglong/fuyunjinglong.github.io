# 微前端

> 1.微前端的 3 种应用场景：巨石应用拆分、跨技术栈聚合、兼容遗留系统；
>
> 2.微前端的 6 种典型实现方式：路由分发式、前端容器化、微应用化、应用组件化、前端服务化和微件化；
>
> 3.微前端的 2 个关键技术：运行时集成和应用隔离；

**1.简介**

微前端是一种类似于微服务的架构，微前端特点：**独立开发，独立部署，独立运行**

1.1 微前端适用范围

- 兼容遗留系统，比如适用 iframe 兼容
- 拆分巨石应用，按照业务拆分，如支付宝
- 聚合小应用，比如目前业界常用的是 npm 库，趋势是模块联邦

| **微前端模式** | **说明**                                                                                                                                                                                                                                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IFrame         | 优点：原生支持、简单易用，天然沙箱； 缺点：类似 MPA，白屏场景多、跨域问题；                                                                                                                                                                           |
| 三方微前端框架 | 蚂蚁 Qiankun、腾讯 Wujie、京东 MicroApp、字节 Garfish 等等 优点：支持当前主流的前端框架、都提供了一定的沙箱能力 缺点：依赖三方框架，不定期处理开源和升级问题；需要根据前端框架进行不同程度的改造适配                                                  |
| 模块联邦       | 基于 ContainerPlugin、ContainerReferencePlugin 和 SharePlugin 的 Webpack5(Vite)能力，支持模块共享、独立构建、集中运行 优点：原生打包支持、模块共享，减少加载文件体积、接近本地应用、去中心化 缺点：没有提供沙箱能力（如果有沙箱的话就没法模块共享了） |
| WebComponents  | 原生技术，主流浏览器都已经支持，仅仅是运行时技术，没有提供打包技术，需要和其他技术（npm、模块联邦、wujie 等）结合使用。可以构建独立运行环境，但不具备 js 沙箱能力                                                                                     |

**2.微前端架构演进**

2.1 微前端的典型实现方式

- 路由分发式和前端容器化
- 微应用化和应用组件化
- 前端微服务化和微件化

**路由分发式和前端容器化**

> **路由分发式**：统一域名，依托反向代理，通过路由将不同的业务分发到不同的独立前端应用上。
>
> **优点**：框架无关，独立开发部署和运行，应用隔离完全
>
> **缺点**：技术栈混乱，无法共享复用，还是烟囱
>
> ---
>
> **前端容器化**，采用 iFrame 技术，将另一个应用/页面嵌入到当前页面中，相互隔离，又可以保持通信
>
> **优点**：简单实用，技术无关，不同应用页面可以聚合
>
> **缺点**：性能和体验一致性都不好

**微应用化和应用组件化**

> **微应用化**：npm 包模式，把应用拆解为单一、微小组件的形式，通过构建系统合并，组合成一个新的前端应用。
>
> **优点**：工程化，组合式集成，成熟的包管理机制
>
> **缺点**：组件包的变更，需要重新编译构建
>
> ---
>
> **应用组件化**：采用 Web Components 技术，开发者创建可重用的定制元素，在 Web 应用中直接使用。
>
> **优点**：未来的 Web 标准，不依赖前端框架
>
> **缺点**：还不成熟，依赖特定浏览器。截至目前 IE 和 Safari 对 Web Components 的支持都不够好。

**前端微服务化和微件化**

> **前端微服务化**：微服务架构在前端的实施，完全独立（技术栈、开发、部署、构建独立），自主运行，最后通过模块化的方式组合出完整的前端应用。
>
> **优点**：不需要使用 IFrame 了
>
> **缺点**：现有的微前端框架（ Single-SPA/Mooa/Qiankun ）尚不支持多应用同时运行
>
> ---
>
> **微件(Widget)化**：参照服务化思路，把完整页面拆解为一个个具有独立业务意义的微件（卡片），并根据不同的用户场景组合出新的页面。
>
> **优点**：只包含业务代码，体积小，加载快，用户体验好
>
> **缺点**：依赖共享，框架强相关，需要有统一的标准规范

2.2 微前端的关键技术

- 模块加载——JS Entry 与 HTML Entry 方式
- 应用隔离

**模块加载——JS Entry 与 HTML Entry 方式**

> **JS Entry**：子应用将资源打成一个 entry script，并将生命周期函数暴露给主应用，主应用检测路由命中子应用的规则之后就会触发其渲染函数，把子应用挂载到相应的 DOM 下。
>
> **HTML Entry**：主应用直接将子应用打出来 HTML 作为入口，然后通过 fetch html 的方式获取子应用的静态资源，同时将 HTML document 作为子节点塞到主应用的容器中。

| **App Entry** | **优点**                                                            | **缺点**                                                                                                                                                                        |
| ------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JS Entry      | 主子应用使用同一个 bundle，可以方便做构建时优化                     | 1.子应用发布时需要主应用重新打包 2.主应用需要为每个子应用预留一个容器节点，且该节点 id 需与子应用的容器 id 保持一致 3.子应用各类资源需要一起打包成一个 bundle，资源加载效率较低 |
| HTML Entry    | 1.子应用开发、发布完全独立 2.子应用具备与独立应用开发一致的开发体验 | 1.多一次请求，子应用资源解析消耗转移到运行时 2.主子应用不处于同一构建环境                                                                                                       |

**应用隔离**

> **CSS 隔离**：利用 Shadow DOM,让一个 DOM 拥有自己的“影子”DOM 树，这个 DOM 树不能在主文档中被任意访问，可以拥有局部样式规则，天然实现了样式隔离。
>
> **JS 隔离**：利用 ES6 的 Proxy 语法，把 window 对象代理到 fakeWindow 上，子应用操作的是 fakeWindow，从而避免对全局 window 对象的污染。

**single-spa**

> Single-spa 是一个将多个单页面应用聚合为一个整体应用的 JavaScript 微前端框架。 核心(注册子应用+路由管理+应用加载器)
>
> 使用 single-spa 进行前端架构设计可以带来很多好处，例如:
>
> •在同一页面上[使用多个前端框架](https://zh-hans.single-spa.js.org/docs/ecosystem) [而不用刷新页面](https://zh-hans.single-spa.js.org/docs/building-applications) ([React](https://zh-hans.single-spa.js.org/docs/ecosystem-react), [AngularJS](https://zh-hans.single-spa.js.org/docs/ecosystem-angularjs), [Angular](https://zh-hans.single-spa.js.org/docs/ecosystem-angular), [Ember](https://zh-hans.single-spa.js.org/docs/ecosystem-ember), 你正在使用的框架)
>
> •独立部署每一个单页面应用
>
> •新功能使用新框架，旧的单页应用不用重写可以共存
>
> •改善初始加载时间，延迟加载代码

**qiankun**

> •**基于** **[single-spa](https://github.com/CanopyTax/single-spa)** 封装，提供了更加开箱即用的 API。
>
> •**技术栈无关**，任意技术栈的应用均可 使用/接入，不论是 React/Vue/Angular/JQuery 还是其他等框架。
>
> •**HTML** **Entry** **接入方式**，让你接入微应用像使用 iframe 一样简单。
>
> •**样式隔离**，确保微应用之间样式互相不干扰。
>
> •**JS** **沙箱**，确保微应用之间 全局变量/事件 不冲突。
>
> •**资源预加载**，在浏览器空闲时间预加载未打开的微应用资源，加速微应用打开速度。
>
> •**umi** **插件**，提供了 [@](https://github.com/umijs/plugins/tree/master/packages/plugin-qiankun)[umijs](https://github.com/umijs/plugins/tree/master/packages/plugin-qiankun)[/plugin-](https://github.com/umijs/plugins/tree/master/packages/plugin-qiankun)[qiankun](https://github.com/umijs/plugins/tree/master/packages/plugin-qiankun) 供 umi 应用一键切换成微前端架构系统

**icestark**

> • **开箱即用**：TypeScript/Webpack5/CSS Modules/Mock/SSR，各种方案 All in One
>
> •**贴合业务的最佳实践**：目录规范、代码规范、路由方案、状态管理、数据请求等
>
> •**多种应用模式**：支持服务端渲染 SSR 以及静态构建 SSG
>
> •**强大的插件能力**：官方所有能力都通过插件实现，业务可以通过插件扩展各种能力
>
> •**丰富的领域方案**：微前端 ICESTARK、一体化方案等

**piral**

> 高度模块化
>

> 全局状态管理

>
> CLI 工具

**emp**

> •基于 Webpack5 模块联邦实现
>
> •每个微应用独立部署运行，
>
> •动态更新微应用：
>
> •去中心化，
>
> •跨技术栈组件式调用，
>
> •按需加载，
>
> •应用间通信，
>
> •生成对应技术栈模板，
>
> •远程拉取 ts 声明文件

**garfish**

> •加载器（Loader）
>
> - HTML 入口类型，拆解 HTML Dom、Script、Style
> - JS 入口类型，提供基础 Dom 容器
> - 负责注册平台侧提供的应用列表
> - 负责加载和解析子应用入口资源
> - 预加载能力
> - 解析子应用导出内容
>
> •沙箱隔离（Sandbox）
>
> - 提供代码执行能力，收集执行代码时存在的副作用
> - 提供销毁收集副作用的能力
> - 支持沙箱多实例，收集不同实例的副作用
>
> •路由托管（Router）
>
> - 解决不同应用间的路由不同步问题
> - 提供路由劫持能力，在主应用上管控子应用路由
> - 提供路由驱动能力来拼装完整的平台的能力
>
> •子应用通信（Store）
>
> - 建立通信桥梁
> - 提供共享机制

**Athena**

> 1.**远程加载**：支持远程按需加载基于 HTML Entry+ESM 技术规范的微模块；
>
> 2.**一模多态**：支持动态配置微模块渲染方式：组件方式、页面方式和应用方式；
>
> 3.**依赖共享**：支持三方件和公共服务依赖共享；
>
> 4.**快速接入**：业务仅需在模块外层非侵入式的做轻量级的包装即可接入微前端框架

**3.业界主流微前端技术方案对比**

| **技术方案**   | **开发成本** | **维护成本** | **可行性** | **技术栈无关** | **实现难度** | **潜在风险**                                                    | **落地实践**                                |
| -------------- | ------------ | ------------ | ---------- | -------------- | ------------ | --------------------------------------------------------------- | ------------------------------------------- |
| 路由分发       | 低           | 低           | 高         | 是             | easy         | 无                                                              | http 服务器反向代理，如 nginx 配置 location |
| iframe         | 低           | 低           | 高         | 是             | easy         | seo 不友好、cookie 管理、通信机制、弹窗问题、刷新后退、安全问题 | SEP、GDE                                    |
| 应用微服务     | 高           | 低           | 中         | 是             | hard         | 共享及隔离粒度不统一                                            | qiankun、icestark 及类 single-spa 应用      |
| 微件化         | 高           | 中           | 低         | 否             | hard         | 实现微件管理机制                                                | icestark                                    |
| 微应用化       | 中           | 中           | 高         | 否             | normal       | 多个项目组合，需要考虑各个部署升级情况                          | EMP                                         |
| Web Components | 高           | 低           | 高         | 是             | normal       | 新 api，浏览器兼容性                                            | Micro-app                                   |

微前端技术选型建议

> Ø**遗留系统需要聚合、涉及多技术栈场景**
>
> 1.如果系统之间相对独立，无耦合，建议采用**iframe**集成方式，技术简单，成本最低；
>
> 2.如果系统之间有交互，并且体验要求较高，建议选用较为成熟的应用微服务框架-**qiankun**；
>
> Ø**单一 SPA 巨石应用，需要拆解场景**
>
> 1.如果拆解的子应用需要能够独立运行，应用之间需要隔离，建议选用**qiankun**或者**icestark**；
>
> 2.如果子应用不考虑独立运行，而更关注更灵活、更细粒度的组装，建议选用**Micro-app**或者**Athena**；
>
> Ø**多个 SPA 应用，烟囱效应明显，需要提取公共底座场景**
>
> 1.如果需要依赖共享，且在构建时聚合，建议选用**EMP**，能够解决多个应用之间的代码共享问题；
>
> 2.如果需要依赖共享且技术栈统一，但需要运行时按需聚合，建议选用**Athena**。
