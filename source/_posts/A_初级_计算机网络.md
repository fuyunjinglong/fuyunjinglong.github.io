## 网络模型(4层)

网络模型主要分为**理论上的 OSI 七层模型**和**实际开发中应用的 TCP/IP 四层模型**

**OSI七层网络模型**

**TCP/IP四层概念模型**

> 1. 应用层
>    - **职责：** 直接为用户的应用进程提供服务，规定应用进程在通信时所遵循的协议。
>    - **常见协议：** HTTP、HTTPS、DNS、FTP、WebSocket。
>    - **数据单元：** 报文。
> 2. 传输层
>    - **职责：** 负责向两个主机中进程之间的通信提供服务，提供端到端的可靠（或不可靠）传输。
>    - **常见协议：** TCP（可靠，面向连接）、UDP（不可靠，无连接）。
>    - **数据单元：** 报文段（TCP）或用户数据报（UDP）。
> 3. 网络层
>    - **职责：** 负责为分组交换网上的不同主机提供通信服务，核心任务是**寻址和路由**（把数据包从源地址送到目的地址）。
>    - **常见协议：** IP、ICMP（Ping就是基于此）、ARP。
>    - **数据单元：** IP数据报/分组。
> 4. 网络接口层（数据链路层 + 物理层）
>    - **职责：** 负责接收 IP 数据报并通过网络发送，或者从物理网络接收帧，抽出 IP 数据报交给网络层。处理硬件层面的电信号或光信号。
>    - **常见协议：** 以太网协议、MAC地址寻址。
>    - **数据单元：** 帧。

**通俗理解**

> - **应用层（买家/卖家）：** 你在淘宝下单，卖家打包好商品并附上发货单（HTTP 报文）。
> - **传输层（快递公司分拣中心）：** 顺丰拿到包裹，贴上快递单，保证包裹不丢、不损坏送达（TCP）。
> - **网络层（跨省运输调度）：** 系统规划路线，从杭州发往北京，决定走航空还是陆运（IP路由）。
> - **网络接口层（货车/飞机司机）：** 实际开车或者开飞机，在两个相邻的站点之间搬运包裹（MAC地址转发）。

## Socket/TCP/HTTP/WebSocket/RPC

> - Socket：只是tcp/ip协议中的一个套接字
> - TCP：面向连接的、可靠的、基于字节流的传输层协议
> - Http：超文本传输协议。短连接，无状态协议
> - WebSocket：长连接，服务端主动推送协议
> - RPC：远程调用方式，具体协议如grpc、Thrift 

## Cookies、SessionStorage和LocalStorage

**定义**

> - cookie 是网站为了标示用户身份而储存在用户本地终端上的数据。cookie 数据始终在同源的http请求中携带，也会在浏览器和服务器间来回传递。
> - sessionStorage 和 localStorage 不会自动把数据发给服务器，仅在本地保存。

**存储大小**

> - cookie 数据大小不能超过 4k。
> - sessionStorage 和 localStorage可以达到 5M 或更大。

**有期时间**

> - cookie 设置的 cookie 过期时间之前一直有效，即使窗口或浏览器关闭。默认是关闭浏览器后失效。
> - sessionStorage 数据在当前浏览器窗口关闭后自动删除。
> - localStorage 存储持久数据，浏览器关闭后数据不丢失除非主动删除数据；



## HTTP是什么

Http是**超文本传输协议**

> - 超文本：超越文本范围，如文字、语音、视频等
> - 传输：双向传输
> - 协议：行为约定和规范

## TCP是什么(3次握手4次挥手)

**1. 核心定义 (一句话概括)**

TCP 是**面向连接的、可靠的、基于字节流**的传输层通信协议。

> - **面向连接**：数据传输前必须先建立连接（三次握手），传输结束后需要释放连接（四次挥手）。
> - **可靠传输**：通过**序列号、确认应答（ACK）、超时重传**等机制，保证数据**无差错、不丢失、不重复、且按序到达**。
> - **流量控制**：利用**滑动窗口**机制，防止发送方发送过快导致接收方缓冲区溢出。
> - **拥塞控制**：当网络拥堵时，通过**慢启动、拥塞避免、快重传、快恢复**等算法，减少向网络注入数据，从而缓解拥塞。

**2.工作原理**

**三次握手**

<img src="/img/image-20230325104746863.png" alt="image-20230325104746863" style="zoom:50%;" />

形象解释

> - A：喂，你能听到我说话吗？（SYN）
> - B：我能听到。那你能听到我说话吗？（SYN + ACK）
> - A：我也能听到。那我们开始聊吧。（ACK）
> - (如果是2次，B 说我能听到后就开始滔滔不绝，但 A 其实手机没信号了，B 就在对着空气说话，**不可行**。)
> - (如果是4次，B 其实可以**一次性把两句话说完**：“我能听到你说话，那你能听到我说话吗？”，两句强行硬拆开，**浪费一次传输**。)

专业解释

序列号能够保证数据包不重复、不丢弃和按序传输。

> **第一次握手([SYN], Seq = x)**
> 客户端发送一个SYN标记的包，Seq初始序列号x，发送完成后`客户端`进入`SYN_SEND`状态。
>
> **第二次握手([SYN,ACK], Seq = y, ACK = x + 1)**
> 服务器返回确认包(ACK)应答，同时还要发送一个SYN包回去。ACK = x + 1,表示确认收到(客户端发来的Seq值 + 1)，Seq = y, 表示让客户端确认是否能收到。发送完成后`服务端`进入`SYN_RCVD`状态。
>
> **第三次握手([ACK], ACK = y + 1)**
> 客户端再次发送确认包(ACK),ACK = y + 1, 表示确认收到服务器的包（服务端发来的Seq值 + 1）。`客户端`发送完毕后，进入`ESTABLISHED`状态，`服务端`接收到这个包，也进入`ESTABLISHED`状态, TCP握手结束。

**四次挥手**

<img src="/img/image-20230325110001138.png" alt="image-20230325110001138" style="zoom:50%;" />

形象解释

> - A：我没啥要说的了，准备挂了。（FIN）
> - B：好的，我知道你没话说了。但我还有两句要说，你先别挂。（ACK）
> - B：好了，我也说完了，我也准备挂了。（FIN）
> - A：好的，那就挂吧。（ACK）
> - (如果是3次，B说“好的，我知道你没啥说的了，我也没啥说的了，一起挂吧！”，**可行**。)
> - (如果是5次，因为没办法拆解了，**不可能出现**。)

专业解释

> **第一次挥手（[FIN], Seq = x）**
> 客户端发送一个FIN标记的包，告诉服务器需要关闭连接，表示自己不用发送数据了，但是还可以接收数据。发送完成后，`客户端`进入`FIN_WAIT_1`状态。
>
> **第二次挥手 ([ACK], ACK = x + 1)**
> 服务端发送一个ACK的确认包，告诉客户端接收到关闭的请求，但是还没有准备好。发送完成后，`服务端`进入`CLOSE_WAIT`状态，`客户端`收到这个包后，进入`FIN_WAIT_2`，等待服务器关闭连接。
>
> **第三次挥手 ([FIN], Seq = y)**
> 服务端准备好关闭连接时，发送FIN标记的包，告诉客户端准备关闭了。发送完成后，`服务端`进入`LAST_ACK`状态，等待客户端确认。
>
> **第四次挥手 ([ACK], ACK = y + 1)**
> 客户端接收到服务端的关闭请求，再发送ACK标记的确认包，进入`TIME_WAIT`状态，等待服务端可能请求重传的ACK包。
> 服务端接收到ACK包后，关闭连接，进入`CLOSED`状态。
> 客户端在等待固定时间(两个最大段生命周期)后，没有接收到服务的ACK包，认为服务器已关闭连接，自己也关闭连接，进入`CLOSED`状态。

**流量控制**：利用滑动窗口实现，接收方通过TCP头部的窗口大小字段告诉发送方自己还有多少缓冲区空间，发送方据此控制发送速率。

**拥塞控制**：包括慢启动、拥塞避免、快重传、快恢复四个部分，旨在避免网络过载。

**3.TCP与UDP对比**

| 特性       | TCP                                        | UDP                          |
| :--------- | :----------------------------------------- | :--------------------------- |
| **连接**   | 面向连接                                   | 无连接                       |
| **可靠性** | 可靠传输（保证顺序、重传、流控、拥塞控制） | 不可靠传输，不保证顺序和到达 |
| **效率**   | 低，开销大（首部20字节）                   | 高，开销小（首部8字节）      |
| **数据**   | 面向字节流                                 | 面向报文                     |
| **应用**   | 文件传输、邮件、网页浏览 (HTTP/HTTPS)      | DNS、视频流、直播、在线游戏  |

## Web漏洞攻防

**一、4大漏洞**

**1. SQL注入**

- **原理**：应用程序将用户输入直接拼接到SQL查询语句中，导致输入的数据被当做SQL代码执行。

- **攻击场景**：攻击者通过构造恶意Payload（如 `' OR 1=1 --`），不仅可以绕过登录认证，还能利用报错注入、盲注窃取数据库敏感信息，甚至利用 `INTO OUTFILE` 写入WebShell获取服务器权限。

- **防御方案**：
  - 根本防御：使用参数化查询（预编译语句），严格区分代码与数据。
  - 辅助防御：对输入进行严格的白名单校验；数据库采用最小权限原则，禁止Web应用使用root权限连接数据库；部署WAF拦截恶意特征。

**2. 跨站脚本攻击（XSS）**

- **原理**：攻击者将恶意JavaScript脚本注入到网页中，当其他用户访问时，脚本在用户浏览器端执行。

- **攻击场景**：分为反射型、存储型和DOM型。攻击者可利用XSS窃取用户Cookie实现会话劫持，或者进行键盘记录、钓鱼等操作。

- **防御方案**：
  - 输入校验与输出编码：根据数据输出位置（HTML、JavaScript、URL等）进行相应的实体编码或转义。
  - 防护机制：配置HttpOnly属性防止Cookie被JS读取；部署严格的CSP（内容安全策略），限制外部脚本加载。

**3. 跨站请求伪造（CSRF）**

- **原理**：攻击者诱导已登录用户在不知情的情况下，向目标网站发送恶意请求，利用用户的身份凭证执行非法操作。

- **攻击场景**：如诱导用户点击带有转账操作的图片链接，浏览器会自动带上用户的Cookie发起请求。

- **防御方案**：
  - Token机制：在请求中加入随机的Anti-CSRF Token，服务端校验Token合法性。
  - 请求头校验：验证HTTP Referer或Origin字段。
  - Cookie属性：设置Cookie的 `SameSite` 属性为 `Strict` 或 `Lax`。

**4. 服务端请求伪造（SSRF）** *（加分项，云原生时代重点）*

- **原理**：服务器提供了从外部获取数据的功能，但未对目标地址进行严格限制，导致攻击者可以伪造服务端发起请求。
- **攻击场景**：探测内网端口、读取内网服务指纹、攻击内网应用；在云环境中，常利用SSRF请求云元数据接口（如AWS的 `169.254.169.254`）窃取云服务器临时凭证。
- **防御方案**：禁止跳转；对请求目标IP进行白名单限制（如仅允许特定公网域名）；禁用非HTTP/HTTPS协议；隔离内网与服务器网络。

**二、整体防御体系**

> 1. 应用层防御：
>    - 安全左移：在开发阶段引入SAST（静态代码扫描）和SCA（软件成分分析），将漏洞扼杀在代码编写阶段。
>    - 网关层：部署WAF（Web应用防火墙）进行常规的SQL注入、XSS拦截。
> 2. 网络层防御：
>    - 通过防火墙、IDS/IPS进行网络隔离和流量监控，确保DMZ区与内网区严格隔离。
> 3. 运维与监控层：
>    - 实施日志集中管理（SIEM），对异常的高频请求、5xx错误激增等进行实时告警。
>    - 建立应急响应机制，一旦发现Web应用被攻破，能快速止损并溯源。”

## 重定向与转发

一句话:重定向时浏览器上的网址改变;转发是浏览器上的网址不变

- 重定向是客户端行为,转发是服务器行为
- 重定向是两次request,请求转发是一次request

## HTTP常见的状态码

> 1xx 是信息性，表示请求已收到，需要继续处理；
> 2xx 表示成功，比如 200、201、204、206；
> 3xx 是重定向，比如 301 永久重定向、302 临时重定向、304 协商缓存；
> 4xx 是客户端错误，比如 400 参数错误、401 未认证、403 无权限、404 资源不存在；
> 5xx 是服务器错误，比如 500 内部错误、502 网关错误、503 服务不可用、504 网关超时。

`1xx` 类状态码属于**提示信息**，是协议处理中的一种中间状态，实际用到的比较少。

`2xx` 类状态码表示服务器**成功**处理了客户端的请求，也是我们最愿意看到的状态。

> - 「**200 OK**」是最常见的成功状态码，表示一切正常。如果是非 `HEAD` 请求，服务器返回的响应头都会有 body 数据。
> - 「**204 No Content**」也是常见的成功状态码，与 200 OK 基本相同，但响应头没有 body 数据。
> - 「**206 Partial Content**」是应用于 HTTP 分块下载或断点续传，表示响应返回的 body 数据并不是资源的全部，而是其中的一部分，也是服务器处理成功的状态。

`3xx` 类状态码表示客户端请求的资源发生了变动，需要客户端用新的 URL 重新发送请求获取资源，也就是**重定向**。

> - 「**301 Moved Permanently**」表示永久重定向，说明请求的资源已经不存在了，需改用新的 URL 再次访问。
> - 「**302 Found**」表示临时重定向，说明请求的资源还在，但暂时需要用另一个 URL 来访问。
> - 「**304 Not Modified**」不具有跳转的含义，表示资源未修改，重定向已存在的缓冲文件，也称缓存重定向，也就是告诉客户端可以继续使用缓存资源，用于缓存控制。

301 和 302 都会在响应头里使用字段 `Location`，指明后续要跳转的 URL，浏览器会自动重定向新的 URL。

`4xx` 类状态码表示客户端发送的**报文有误**，服务器无法处理，也就是错误码的含义。

> - 「**400 Bad Request**」表示客户端请求的报文有错误，但只是个笼统的错误。
> - 「**403 Forbidden**」表示服务器禁止访问资源，并不是客户端的请求出错。
> - 「**404 Not Found**」表示请求的资源在服务器上不存在或未找到，所以无法提供给客户端。

`5xx` 类状态码表示客户端请求报文正确，但是**服务器处理时内部发生了错误**，属于服务器端的错误码。

> - 「**500 Internal Server Error**」与 400 类型，是个笼统通用的错误码，服务器发生了什么错误，我们并不知道。
> - 「**501 Not Implemented**」表示客户端请求的功能还不支持，类似“即将开业，敬请期待”的意思。
> - 「**502 Bad Gateway**」通常是服务器作为网关或代理时返回的错误码，表示服务器自身工作正常，访问后端服务器发生了错误。
> - 「**503 Service Unavailable**」表示服务器当前很忙，暂时无法响应客户端，类似“网络服务正忙，请稍后重试”的意思。

**经典对比**

> 1. 301 vs 302
>
> - 301：永久重定向，浏览器会**缓存**新地址，下次直接访问新 URL；搜索引擎会把权重转移到新地址。
> - 302：临时重定向，浏览器**不缓存**跳转，下次还访问原 URL；搜索引擎不会更新索引。
>
> 适用：换域名、站点迁移 → 用 301。临时活动页、登录跳转 → 用 302/307。
>
> 2. 401 vs 403
>
> - 401：未认证（你是谁？）。解决：让用户登录、刷新 Token。
> - 403：已认证但无权（我知道你是谁，但你不能进）。解决：联系管理员开通权限，或提示权限不足。
>
> 3. 304 vs 200
>
> - 200：服务器返回完整资源，浏览器重新下载。
> - 304：服务器告诉浏览器“资源没变，用缓存”，客户端直接使用本地缓存，减少传输，优化性能。

## HTTP/1、HTTP/2、HTTP/3

| 版本         | 底层协议  | 核心并发机制          | 队头阻塞 | 头部处理     |
| :----------- | :-------- | :-------------------- | :------- | :----------- |
| **HTTP/1.1** | TCP       | 多个 TCP 连接 (6-8个) | HTTP层有 | 明文，冗余大 |
| **HTTP/2**   | TCP       | 单连接多路复用        | TCP层有  | HPACK 压缩   |
| **HTTP/3**   | QUIC(UDP) | 单连接多路复用        | 基本消除 | QPACK 压缩   |

**一、 HTTP/1.1：长连接与并发连接的探索**

**1. 核心特性：**

- **长连接**：默认开启 `Keep-Alive`，一个 TCP 连接可以发送多个请求，减少了频繁建连的开销。
- **管线化**：允许客户端在未收到上一个响应时就发送下一个请求。
- **并发连接**：浏览器允许对同一域名建立 6~8 个 TCP 连接并行加载资源。

**2. 遗留痛点：**

- **HTTP 层队头阻塞**：虽然有了管线化，但服务器必须按请求顺序返回响应。第一个请求慢，后面的全得等。因此现代浏览器基本默认禁用了管线化。
- **头部冗余严重**：每次请求都要携带大量重复的明文头部（如 Cookie、User-Agent），非常浪费带宽。

**二、 HTTP/2：二进制分帧与多路复用**

**1. 核心特性：**

- **二进制分帧**：将数据拆分为更小的二进制帧进行传输，取代了明文格式，提升了机器解析效率。
- **多路复用**：在**单个 TCP 连接**上，可以同时并发多个请求和响应。帧带有 Stream ID，接收端按 ID 重新组装，彻底解决了 HTTP 层的队头阻塞。
- **头部压缩（HPACK）**：客户端和服务端共同维护一张头信息表，只发送差异数据，大幅减小头部体积。
- **服务器推送**：服务器可以在客户端请求 HTML 时，主动推送 CSS、JS 等依赖资源。

**2. 遗留痛点：**

- **TCP 层队头阻塞**：HTTP/2 底层依然基于 TCP。当发生丢包时，TCP 协议会暂停所有数据传递等待重传。这导致在弱网或高丢包率环境下，HTTP/2 的表现甚至可能不如 HTTP/1.1 的多连接。
- **握手延迟**：建立连接需要 TCP 三次握手 + TLS 握手，延迟依然较高。

**三、 HTTP/3：拥抱 QUIC 协议**

HTTP/3 进行了颠覆性重构，底层放弃了 TCP，转而使用基于 UDP 的 **QUIC 协议**。

**1. 核心特性：**

- **彻底解决队头阻塞**：QUIC 将流的概念下沉到传输层，各个流相互独立。一个流丢包只会阻塞该流，不影响其他流。
- **更快的连接建立**：将传输层握手和加密握手合并，首次连接只需 1-RTT，配合缓存甚至能做到 0-RTT。
- **连接迁移**：基于连接 ID 而非 IP/端口来标识连接。当手机在 Wi-Fi 和 4G 间切换时，IP 变了但连接不断，实现无缝网络切换。

**2. 现状与挑战：**

- 很多老旧网络设备或防火墙对 UDP 流量优化不足或有限制，HTTP/3 的全面普及仍需时间。

## 从输入URL到页面渲染完成过程

分为两大阶段：

- 网络阶段

  > DNS → TCP → TLS → HTTP。
  >
  > 浏览器解析 URL → DNS 域名解析 → 建立 TCP 连接（HTTPS 时进行 TLS 握手）→ 发送 HTTP 请求 → 服务器处理并返回响应；

- 渲染阶段

  > 解析 HTML 构建 DOM → CSSOM → 渲染树 → Layout → Paint → Composite。
  >
  > 浏览器解析 HTML 构建 DOM → 解析 CSS 构建 CSSOM → 合并生成渲染树 → 布局（Layout，计算位置与尺寸）→ 绘制（Paint）→ 合成（Composite），最终呈现到屏幕。过程中 JS 的执行会阻塞 DOM 解析，CSS 的解析会阻塞首次渲染。

> **服务端处理（关键）**：请求首先到达 **Nginx 反向代理**。Nginx 负责静态资源直接返回、负载均衡、SSL 卸载等；动态请求则转发给后端应用服务器（如 Node.js/Java）处理业务逻辑，完成后返回给 Nginx，由 Nginx 统一进行压缩、加响应头后回传。

**1）网络阶段**

- **URL 解析**：判断输入的是搜索词还是合法地址，补全协议（https）、域名等。
- **DNS 解析**：浏览器/系统/路由器缓存查找，未命中则递归查询根/顶级/权威 DNS 服务器，获取服务器 IP（通常是 Nginx 所在服务器的 IP）。
- **建立连接**：进行 TCP 三次握手；若是 HTTPS，进行 TLS 握手（建立安全通道）。
- **发送请求**：浏览器构建 HTTP 请求报文（含请求行、请求头、Cookie 等）发送出去。

**2）解析与渲染阶段（关键渲染路径 CRP）**

- **构建 DOM**：浏览器解析 HTML，遇到 `<script>` 会默认暂停解析并执行（阻塞）。
- **构建 CSSOM**：解析 CSS，生成样式规则树。CSSOM 未完成会阻塞渲染，防止 FOUC（样式闪烁）。
- **生成渲染树**：合并 DOM 和 CSSOM，只包含可见节点。
- **布局**：计算节点在屏幕上的几何信息（位置、大小）。
- **绘制**：将节点的样式（颜色、背景等）填充到像素中。
- **合成**：将图层按正确顺序叠加，通过 GPU 显示在屏幕上。

**3）资源加载与交互**

- 并行加载与执行：图片、字体等资源异步加载，不阻塞首次渲染；JS 可能触发 DOM/CSS 变化，导致回流或重绘。
- 事件循环：主线程通过事件循环管理宏任务与微任务，响应用户交互并调度渲染。
- 连接管理：TCP 可复用（keep-alive），页面关闭时通过四次挥手断开连接。

## 彻底搞懂Https

**HTTPS 本质上就是 `HTTP + SSL/TLS`**。它在 HTTP 和 TCP 之间加了一层安全层，通过**“非对称加密交换对称密钥 + 数字签名防篡改 + 数字证书防假冒”**这套组合拳，解决了 HTTP 明文传输带来的安全问题。

**非对称加密**

> - 定义：有两把密钥，公钥加密私钥解密(或私钥加密公钥解密)。服务端有公钥和私钥，服务端发送公钥给服务端。
> - 缺点：黑客劫持公钥后，客户端到服务端安全，服务端到客户端，黑客有公钥，能解开服务端发给客户端的数据。

**对称加密**

> - 定义：只有一把密钥，(客户端)加密，(服务端)解密
> - 缺点：秘钥传输过程中，被黑客劫持，就能用秘钥解开双方加密的内容

**完整加密流程**

> 1. (RSA、ECC)原理：在握手阶段使用。客户端和服务器通过非对称加密安全地协商出一个“对称密钥”。
>    - 服务器存在公钥和密钥，发送公钥给客户端
>    - 客户端随机生成一个“对称密钥”，用这个公钥对其加密，发送给服务端
> 2. (AES)原理：在数据传输阶段使用。双方使用刚才协商出的“对称密钥”对数据进行加解密。对称加密速度快，适合大量数据传输。
> 3. 防篡改
>    - 12存在的问题：黑客拦截服务器发送到客户端的内容，并修改，客户端收到后以为还是服务端的指令，其实内容被换成黑客的攻击内容。
>    - 解决：**数字签名** = 你自己的**专属印章**。服务器发送到客户端时，打上服务器的标记，客户端拿出公钥对比标记，就知道内容有没有被人动过了。
> 4. 防冒充
>    - 3存在的问题：**专属印章**可能是假的。黑客拦截服务端发送的“对称密钥”，并替换为“假的对称密钥”发给客户端，黑客用“假的对称密钥”能解开双方加密的内容。
>    - 解决：**数字证书** = 公安局发的**身份证**。服务端在发送“对称密钥”时，用数字证书私钥盖个章，客户端拿现有的“全国各大公安局的印章模板”公钥（浏览器内置的根证书），两者一比对就知道，客户端就知道“对称密钥”是来自本服务端，而不是来自黑客的服务器。

## RPC是什么

HTTP 用于外网（浏览器到服务器）通信，RPC 用于内网微服务（服务器到服务器）通信。有 HTTP 还要 RPC，主要是为了解决微服务间**高频调用的性能损耗**和**开发体验**问题。

**Http与RPC对比**

> 1. **序列化效率更高**：HTTP 多用 JSON（文本格式，体积大，解析慢）；RPC 多用 Protobuf（二进制，体积小，解析极快）。
> 2. **协议开销更小**：HTTP 请求头冗长，对纯后端调用是无效开销；RPC 常基于精简的 TCP 私有协议或 HTTP/2，报文头极小。
> 3. **开发体验更好**：RPC 将网络调用抽象为“本地函数调用”（基于 IDL 自动生成代码），屏蔽拼装 URL 等网络细节，且自带强类型。
> 4. **治理生态更全**：RPC 框架天生集成服务发现、负载均衡、熔断限流，HTTP 需额外引入组件拼装。

**总结**

> - **对外用 HTTP**：通用、跨语言、易调试。
> - **对内用 RPC**：极致性能、强类型、屏蔽网络细节、自带微服务治理。
> - 现在两者正在融合，比如 **gRPC** 本质就是 `HTTP/2 + Protobuf`，既保留了通用性又达到了 RPC 的性能。

## WebSocket是什么

WebSocket 是一种在单个 TCP 连接上进行**全双工**通信的协议。它被设计用于在 Web 浏览器和服务器之间进行实时、双向的数据传输。为了解决Http单向通信痛点而生。

**Http与WebSocket对比**

> 1. **通信方向不同**：HTTP 只能由客户端主动发请求，服务器被动答；WebSocket 建立连接后，服务器可以随时**主动推送**数据，实现真正的全双工通信。
> 2. **避免轮询的巨大开销**：用 HTTP 模拟实时通信只能靠“轮询”（客户端不断发请求询问），极其浪费带宽和服务器资源；WebSocket 保持长连接，按需推送，效率极高。
> 3. **协议头部更小**：HTTP 每次请求都要带冗长的 Header；WebSocket 握手后，数据帧的头部只有 2~10 字节，传输成本极低。
> 4. **原生支持二进制**：HTTP 主要是文本传输；WebSocket 原生支持发送和接收二进制数据（ArrayBuffer / Blob），适合音视频流等场景。

**总结**

> - **HTTP**：适合普通的页面加载、数据 CRUD 等低频请求场景。
> - **WebSocket**：适合聊天室、在线协同编辑、股票行情等高频、实时双向交互场景。
> - WebSocket 并非独立于 HTTP，它的**握手阶段复用了 HTTP 协议**（通过携带 `Upgrade: websocket` 请求头），服务器同意升级（101 状态码）后，连接就转变为 TCP 全双工通道了。

## TCP 拆包粘包

**一、定义**

常见误区：**粘包不是 TCP 协议的 bug**，而是"字节流"与"消息边界"之间的语义错位。TCP 压根没有"包"的概念，所谓的"粘"和"拆"，只是应用层拿到的 read() 结果和发送时的逻辑单元对不上号而已

> TCP 拆包粘包的本质是 **TCP 面向字节流、没有消息边界**：发送方多次写入的数据可能被合并成一段发送（粘包），一条完整消息也可能被拆成多段接收（拆包/半包），接收方必须由应用层自己定义消息边界才能正确拆分。这并非 TCP 的缺陷，而是它的设计特性——TCP 只保证字节有序、可靠地到达，不关心"消息"这个上层概念

**二、产生原因对比**

注意：Nagle 只是**提高**了粘包出现概率的诱因之一，即使 `TCP_NODELAY` 禁用它，接收缓冲区的累积机制仍可能导致粘包——所以**关 Nagle 不能从根本上解决问题**

| 触发端 | 具体原因                                                     | 导致现象 |
| ------ | ------------------------------------------------------------ | -------- |
| 发送端 | **Nagle 算法**（默认开启）：存在未确认的小包时，新写入的小数据会被缓存，直到攒够 MSS 或收到前序 ACK 才一次性发送csdn.net+1 | 粘包     |
| 发送端 | **发送缓冲区（SO_SNDBUF）**：多次 write 的小数据在内核缓冲区里连续排布，TCP 取出时可能跨多个逻辑消息tencent.com+1 | 粘包     |
| 发送端 | **MSS/MTU 限制**：以太网 MTU=1500，扣除头部后 MSS≈1460 字节，超出即被分段csdn.net+1 | 拆包     |
| 接收端 | **接收缓冲区（SO_RCVBUF）累积**：应用层 read() 不及时，多个消息在缓冲区中拼接，一次 read 读到多包tencent.com+1 | 粘包     |
| 接收端 | **滑动窗口流量控制**：接收窗口变小，发送方被迫把一次写入的数据分批发送tencent.com+1 | 拆包     |

**三、解决方案（应用层定义消息边界）**

> **核心思路只有一句话：既然 TCP 不给你边界，应用层就自己定一个协议约定。** 主流做法有三种，选型取决于消息特征和开发成本

**方案一：定长法**

约定每条消息固定 N 字节，不足补 0 或空格，接收方每次读 N 字节。

> - 优点：实现最简单，解析 O(1)。
> - 缺点：浪费带宽（短消息要填充），无法承载变长内容。
> - 适用：消息长度天然固定的场景，如传感器周期性上报、工业控制帧

```js
// 接收端伪代码：循环按固定长度切分
while (recv_buf_len >= FIXED_MSG_LEN) {
    memcpy(msg, recv_buf, FIXED_MSG_LEN);
    process(msg);
    memmove(recv_buf, recv_buf + FIXED_MSG_LEN, recv_buf_len - FIXED_MSG_LEN);
    recv_buf_len -= FIXED_MSG_LEN;
}
```

**方案二：分隔符法**

在每条消息末尾追加特殊分隔符（如 `\n`、`\r\n`、`\r\n\r\n`），接收方扫描字节流按分隔符切分。

> - 优点：支持变长消息，文本协议里直观可读。
> - 缺点：分隔符不能出现在消息内容中，否则必须转义（如 Base64 编码后再传输）；二进制数据几乎无法使用；扫描效率偏低。
> - 适用：文本类协议，典型如 FTP、SMTP、Redis、HTTP 头部用 `\r\n\r\n` 分隔

**方案三：长度字段法（Length-Prefixed）**⭐

消息分为 **Header + Body**，Header 固定长度存放 Body 的字节数，接收方先读 Header 解析出长度，再精确读取对应字节数的 Body。

> - 优点：支持任意变长消息、无分隔符冲突、解析高效，是二进制协议的通用标准。
> - 缺点：需要约定 Header 格式，实现略复杂。
> - 适用：绝大多数 TCP 应用——RPC 框架（Dubbo、gRPC）、IM、游戏服务器、自定义私有协议

```js
// 发送端：4 字节长度头 + 消息体
void send_msg(int fd, const char *body, uint32_t len) {
    uint32_t nlen = htonl(len);
    write(fd, &nlen, 4);
    write(fd, body, len);
}

// 接收端：先读 4 字节，再按长度读 Body
uint32_t nlen;
read_full(fd, &nlen, 4);                    // 必须循环读满 4 字节
uint32_t len = ntohl(nlen);
char *buf = malloc(len);
read_full(fd, buf, len);                    // 必须循环读满 len 字节
```

**四、Netty 开箱即用的解码器**

Netty 把上述三种方案封装成现成的解码器，按 pipeline 一行代码接入即可，无需重复造轮子

| 解码器                                                 | 对应方案             |
| ------------------------------------------------------ | -------------------- |
| `FixedLengthFrameDecoder`                              | 定长法               |
| `LineBasedFrameDecoder` / `DelimiterBasedFrameDecoder` | 分隔符法             |
| `LengthFieldBasedFrameDecoder`                         | 长度字段法（最常用） |

**LengthFieldBasedFrameDecoder 配置示例**——处理"4 字节长度头 + 消息体"的典型协议：

```js
ch.pipeline().addLast(new LengthFieldBasedFrameDecoder(
        1024 * 1024,  // maxFrameLength：单帧最大长度，防恶意超大包
        0,            // lengthFieldOffset：长度字段从第 0 字节开始
        4,            // lengthFieldLength：长度字段占 4 字节
        0,            // lengthAdjustment：长度值含义调整（0 表示长度字段只描述 Body）
        4             // initialBytesToStrip：解码后剥掉前 4 字节长度头
));
ch.pipeline().addLast(new MyBusinessHandler());
```

该解码器会自动处理粘包和半包：如果字节流里一次送来 3 条消息，它会拆出 3 帧；如果只送来半条，它会暂存等下一批数据凑齐再交付

**五、选型建议**

> - **新设计的二进制协议** → 长度字段法，通用性和效率最优；
> - **文本/命令行交互**（日志、Redis 客户端）→ 分隔符法最直观；
> - **传感器或工业设备**数据长度天然固定 → 定长法最省事；
> - **不想自己实现** → 直接用 Netty 的 `LengthFieldBasedFrameDecoder`，或改用 HTTP/WebSocket/gRPC 这类已内置边界处理的高层协议











## 正向代理和反向代理

| 对比维度           | 正向代理                          | 反向代理                                  |
| ------------------ | --------------------------------- | ----------------------------------------- |
| **代理对象**       | 客户端                            | 服务器                                    |
| **所处位置**       | 客户端与互联网之间                | 互联网与服务器之间                        |
| **谁感知它的存在** | 服务器感知，客户端需主动配置      | 客户端感知，客户端完全透明无需配置        |
| **隐藏的是谁**     | 隐藏真实客户端 IP                 | 隐藏真实服务器 IP 和后端架构              |
| **核心目的**       | 突破限制、保护隐私、访问控制      | 负载均衡、安全防护、性能优化              |
| **典型工具/示例**  | Squid、Shadowsocks、VPN、爬虫代理 | Nginx、HAProxy、CDN 节点、网关（Gateway） |

**正向代理（Forward Proxy）**

**一、定义**

本质：替客户端向服务器发请求

> 正向代理位于**客户端与互联网之间**，代表客户端向目标服务器发起请求。目标服务器只能看到代理的 IP 地址，看不到背后真实客户端的身份

**二、工作流程**

> 1. 客户端主动配置代理地址，把请求发给正向代理；
> 2. 代理以自己的名义向目标服务器发起请求；
> 3. 目标服务器响应给代理；
> 4. 代理再把响应转回客户端

**三、应用场景**

> - **突破访问限制**：绕过地域封锁或防火墙，访问外部资源。
> - **隐藏客户端 IP**：保护用户隐私，避免被目标网站追踪。
> - **访问控制与内容过滤**：企业内网通过代理统一管理员工的上网行为，过滤不合规内容。
> - **缓存加速**：代理缓存常用资源，重复请求时直接返回，节省带宽



**反向代理（Reverse Proxy）**

**一、定义**

本质：替服务器接收客户端的请求

> 反向代理部署在**服务器端**，位于公网与后端服务器集群之间，代表服务器接收来自客户端的请求。客户端以为自己在和真实服务器通信，实际上面对的是反向代理，后端架构完全被隐藏

**二、工作流程**

> 1. 客户端把请求发到反向代理（以为它就是目标服务器）；
> 2. 代理根据规则（负载、路径等）把请求转发给某台后端服务器；
> 3. 后端服务器处理后把响应交给代理；
> 4. 代理把响应返回客户端

**三、应用场景**

> - **负载均衡**：把海量请求分发到多台后端服务器，避免单点过载，是大型网站和高并发服务的标配。
> - **安全防护**：隐藏真实服务器 IP 和架构，抵御 DDoS 攻击，充当统一入口防火墙。
> - **SSL/TLS 卸载**：集中处理加解密，减轻后端服务器压力。
> - **静态资源缓存与 CDN**：缓存 CSS/JS/图片等静态内容，加快响应速度

## 猫-路由器-交换机

```
光纤 → 光猫(光电转换) → 路由器(拨号/NAT/防火墙) → 交换机(端口扩展) → 电脑
```

> - **光猫**先把光纤里的光信号转成电信号，让运营商的线路能和家庭网线对接；
> - **路由器**拿到电信号后，通过 PPPoE 拨号获取公网 IP，对内做 NAT 转换和 DHCP 分配，对外提供防火墙隔离；
> - **交换机**接到路由器的 LAN 口，把一个网口扩展成多个，让台式机、NAS、机顶盒都能接入同一个局域网
> - **电脑**：连接交换机的口

## 前端缓存

**参考**

> - [一文读懂http缓存（超详细）](https://www.jianshu.com/p/227cee9c8d15)

**定义**

> - Http缓存(优先)
>   - 强缓存
>   - 协商缓存
> - 浏览器缓存
>   - 本地存储
>   - 默认缓存

**缓存术语**

> - 缓存命中率：从缓存中得到数据的请求数与所有请求数的比率
> - 过期内容：超过设置的有效时间。过期内容不能用于回复客户端的请求，必须重新向源服务器请求新内容
> - 验证：验证缓存中的过期内容是否仍然有效，验证通过的话刷新过期时间
> - 失效：失效就是把内容从缓存中移除。当内容发生改变时，必须移除失效的内容

**一、Http缓存**

![image-20230325081435596](/img/image-20230325081435596.png)

HTTP 缓存主要是针对 HTML、CSS、JS、图片等静态资源的缓存。它分为**强缓存**和**协商缓存**。

**1. 强缓存**

> - **特点：** 不需要向服务器发送请求，直接从浏览器本地读取。状态码显示 `200 OK (from disk/memory cache)`。
> - 核心字段：
>   - `Expires`（HTTP/1.0）：设置绝对过期时间，受客户端时间影响，已逐步淘汰。
>   - `Cache-Control`（HTTP/1.1）：设置相对过期时间（如 `max-age=3600`），优先级高于 `Expires`。
>     - `no-cache`：跳过强缓存，走协商。
>     - `no-store`：禁止缓存任何内容。
>     - `public` / `private`：谁可以存。
>     - `max-age`：缓存有效期。

**2.协商缓存**

> - **特点：** 强缓存失效后，浏览器携带缓存标识向服务器询问资源是否更新。若未更新返回 `304 Not Modified`，若更新返回 `200` 和新资源。
> - 核心字段：
>   - `Last-Modified` / `If-Modified-Since`：基于文件修改时间判断，精度为秒，存在误差。
>   - `ETag` / `If-None-Match`：基于文件内容哈希值判断，精度更高，优先级高于 `Last-Modified`。

**二、浏览器缓存**

浏览器缓存是指利用浏览器提供的存储接口，将数据保存在本地。

**1.本地存储**

> - Cookie：
>   - **特点**：容量小（约 4KB），随请求自动发送给服务器，可设置过期时间。
>   - **场景**：用于维持会话状态（如 SessionID）、身份认证。
> - Web Storage（localStorage / sessionStorage）：
>   - **特点**：容量大（约 5MB），仅存本地不随请求发送，API 简单。
>   - 区别：
>     - `localStorage`：永久存储，除非手动清除，适合存 Token、主题配置等持久数据。
>     - `sessionStorage`：会话级存储，关闭标签页即清除，适合存表单数据、临时状态。
> - IndexedDB：
>   - **特点**：容量极大（可达 GB 级），支持异步，支持事务和索引。
>   - **场景**：存储大量结构化数据，如离线应用、文件存储。

**2.默认缓存**

这里指浏览器自身的缓存行为或特殊缓存机制，通常不由开发者代码直接控制，但对性能有重要影响。

> - 启发式缓存：
>   - **定义**：当 HTTP 响应头没有明确缓存策略（没有 Cache-Control 和 Expires）时，浏览器会根据 `Last-Modified` 时间计算一个缓存时间（通常是 `(Date - Last-Modified) * 10%`）。
>   - **影响**：这是一种不可控的缓存行为，容易导致资源更新不及时，因此生产环境建议明确配置 Cache-Control 来规避。
> - 内存缓存与 磁盘缓存：
>   - **Memory Cache**：存储在内存中，读取速度极快，但关闭 Tab 页即释放。浏览器会自动将当前页面中可能复用的资源（如图片、预加载资源）放入内存。
>   - **Disk Cache**：存储在磁盘中，容量大，持久化存储。
>   - **控制**：浏览器根据资源优先级和系统内存状态自动选择存储位置，开发者可通过 Service Worker 或特定的请求头（如 `Vary`）影响其行为。
> - Service Worker Cache：
>   - **定义**：PWA 的核心，允许开发者拦截网络请求并自定义缓存策略。
>   - **特点**：脱离主线程，提供可编程的缓存控制。

## Nginx

**一、定义**

> Nginx（读作 engine-x）是一款高性能的 Web 服务器软件，同时也是反向代理、负载均衡器和 HTTP 缓存的经典实现，由俄罗斯程序员 Igor Sysoev 为解决 **C10K 问题**（单机处理 1 万个并发连接）而开发

**二、四大核心功能**

**静态资源服务器（Web Server）**

> 托管 HTML、CSS、JS、图片等静态文件，利用 sendfile 零拷贝技术直接从磁盘送到网卡，性能极高。基准测试中 Nginx 每秒可处理的静态请求是 Apache 的 2-3 倍

**反向代理与负载均衡**

> 作为服务器集群的统一入口，把请求按权重、轮询、最少连接数等策略分发到多台后端服务器。后端可以是 HTTP、HTTPS、FastCGI、uwsgi、gRPC 乃至 TCP/UDP 协议

**HTTP 缓存与内容加速**

> 对后端响应和静态资源进行缓存，可作为 CDN 边缘节点，加快响应速度、减轻后端压力

**安全防护与 SSL/TLS 卸载**

> 作为统一入口隐藏真实服务器 IP，集中处理 SSL/TLS 加解密（TLS 终结），支持 IP 访问控制、HTTP Basic 认证、Referer 验证等

**三、事件驱动架构(为什么快)**

传统服务器（如 Apache 经典模式）是"一个连接一个进程/线程"，连接一多就会因为频繁的上下文切换和内存开销而崩溃

Nginx 则采用 **Master-Worker 多进程 + 异步非阻塞事件驱动**架构：

> - 一个 Master 进程负责读取配置、管理 Worker；
> - 每个 Worker 进程通过 Linux 的 **epoll**（BSD 下是 kqueue）同时监听数千个连接，谁有事件就处理谁，不会傻等；
> - 单个 Worker 进程的内存占用只有几 MB，单机可稳定支撑 2-3 万并发连接，理论峰值 5 万。

**四、Nginx vs Apache**

实践中两种服务器也常**组合使用**：Nginx 在最前面做反向代理和 SSL 终结，把动态请求转发给后面的 Apache 处理，各取所长

| 对比维度       | Nginx                                     | Apache                                                       |
| -------------- | ----------------------------------------- | ------------------------------------------------------------ |
| **架构**       | 事件驱动 + 异步非阻塞                     | 进程/线程按连接分配（prefork / worker / event MPM）lycoristechnologies.com |
| **高并发表现** | 内存占用低且可预测，万人并发轻松env.dev   | 高并发下内存随连接数增长，性能下降tutorialspoint.com         |
| **静态文件**   | 显著更快（sendfile 零拷贝）               | 较慢env.dev                                                  |
| **动态内容**   | 转发给外部进程（PHP-FPM、uWSGI 等）       | 通过 mod_php 等模块内嵌运行，简单直接env.dev                 |
| **配置灵活性** | 集中式配置，不支持 .htaccess              | 支持 .htaccess 按目录覆盖，适合共享主机lycoristechnologies.com |
| **模块生态**   | 相对精简，但反向代理/负载均衡为"一等公民" | 模块极多、生态成熟tutorialspoint.com                         |
| **典型场景**   | 高并发网站、反向代理、容器/云原生         | 共享主机、传统 PHP 应用、需要 .htaccess 的项目mgsoftware.nl  |

**五、负载均衡算法**

内置 **5 种负载均衡算法**：轮询（round-robin，默认）、加权轮询、ip_hash、least_conn、random（含 two-choice 变体），另有 least_time 等高级算法仅供商业版 NGINX Plus 使用。

**1.算法对比**

| 算法            | 配置关键字                     | 分发原理                                                     | 会话保持      | 适用场景                                             |
| --------------- | ------------------------------ | ------------------------------------------------------------ | ------------- | ---------------------------------------------------- |
| 轮询            | 默认，无需指令                 | 按列表顺序逐个分发                                           | ❌             | 后端性能相近、无状态服务nginx.org                    |
| 加权轮询        | `weight=N`                     | 按 weight 比例分发，权重高的服务器获得更多请求               | ❌             | 后端硬件配置不均（如 8 核 vs 16 核）nginx.org+1      |
| ip_hash         | `ip_hash;`                     | 对客户端 IP 做哈希，IPv4 取前 3 个八位组（/24 网段），固定映射到某台后端 | ✅（基于 IP）  | 后端存本地 Session、无法共享存储nginx.com+1          |
| 最少连接        | `least_conn;`                  | 把请求分给当前活跃连接数最少的服务器；带 weight 时按权重比例折算 | ❌             | 请求处理时长差异大（如长短请求混合）nginx.org+1      |
| 随机 / 两次随机 | `random;` / `random two <key>` | 随机挑选；`two` 模式随机抽 2 台选较空闲者，避免"羊群效应"    | ❌             | 多个独立负载均衡器、容器化环境分发到同一组服务f5.com |
| 最少时间        | `least_time;`                  | 综合最少连接与最低平均延迟（可按 connect / first_byte / last_byte 计算） | ❌             | NGINX Plus 专属，延迟敏感型场景nginx.com             |
| 通用哈希        | `hash $key [consistent];`      | 按自定义变量（如 URI、Cookie）哈希；加 `consistent` 启用 ketama 一致性哈希 | ✅（基于 key） | 缓存服务器分组、需要精细化粘性策略nginx.com          |

**2.代码示例**

> 常用服务器参数：`weight`（权重，默认 1）、`max_fails`（N 次失败判定不可用）、`fail_timeout`（失败判定与恢复探测的时间窗）、`backup`（备用机）、`down`（手动下线）

```js
http {
    upstream backend {
        # 加权轮询 + 最少连接 可同时声明，按权重折算
        least_conn;

        server 192.168.1.10:8080 weight=5 max_fails=3 fail_timeout=30s;
        server 192.168.1.11:8080 weight=2;
        server 192.168.1.12:8080 backup;   # 备用节点，主节点全挂时启用
        server 192.168.1.13:8080 down;     # 标记下线，配合 ip_hash 时不破坏会话
    }

    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend;
            proxy_set_header Host              $host;
            proxy_set_header X-Real-IP         $remote_addr;
            proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
            proxy_next_upstream error timeout http_502;  # 失败自动重试下一台
        }
    }
}
```

**3.ip_hash 注意事项**

```js
upstream sticky_backends {
    ip_hash;
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080 down;  # 用 down 而非删除，保留哈希槽位
}
```

ip_hash 是开源版实现会话保持的最简单方式，但有三个容易踩坑的局限：

> - **NAT 共享 IP 失真**：公司内网、运营商 NAT 或多层代理下，大量用户共享同一个出口 IP，会被全部路由到同一台后端，导致负载倾斜；
> - **IP 变化丢失会话**：手机切 Wi-Fi、移动网络切换后客户端 IP 改变，会话会被重新哈希到另一台服务器；
> - **增减节点全量重哈希**：直接增删 server 会让几乎所有会话重新映射；临时下线请用 `down` 标记保留哈希槽位。

**替代方案**：更可靠的做法是后端把 Session 存到 Redis/Memcached 等共享存储，或使用基于 Cookie 的粘性策略（开源版可用 `hash $cookie_xxx`，商业版有 `sticky cookie` 指令）

**4.选型建议**

> - **无状态 API / 微服务** → 默认轮询或 `least_conn` 即可，配合 `proxy_next_upstream` 实现故障自动转移；
> - **后端性能参差不齐** → 加权轮询，权重按 CPU 核数或压测吞吐比配置；
> - **长请求、流式处理、WebSocket** → `least_conn`，避免慢请求堆积在某台机器上；
> - **后端存本地 Session** → `ip_hash`，但生产环境更推荐把 Session 外置到 Redis，彻底摆脱粘性约束；
> - **缓存类服务（如图片、静态资源后端）** → `hash $request_uri consistent;`，节点增减时仅部分缓存失效；
> - **多活负载均衡器 / 容器多副本代理** → `random two`，避免多实例间同步连接数状态的复杂性
