# 初级

## 前端架构演进

**1.定义**

前端经历了从**‘无架构’的页面开发**，到**‘前后端分离’的工程化开发**，再到如今**‘全栈化、智能化’的架构体系**的过程。这个演进过程大体可以分为四个关键阶段。



**2.核心阶段**

**第一阶段：后端主导时代 - MPA (Web 1.0)**

- **技术栈：** 静态 HTML + CSS，后端模板引擎。
- **特征：** 所有内容由后端在服务器拼接好 HTML，浏览器只负责展示。前端也就是“切图仔”。
- **解决的问题：** 简单、直接，兼容性好。
- **遗留的痛点：** 交互体验差，每次操作都要刷新页面；前端与后端代码高度耦合，前端无法独立开发。

**第二阶段：前后端分离与 AJAX 时代 - SPA 萌芽**

- **技术栈：** jQuery, AJAX, MVC 框架 (Backbone.js, AngularJS 1.x)。
- **特征：** **AJAX** 的出现是转折点。页面不再整体刷新，而是异步请求数据局部更新。前端开始负责复杂的逻辑处理，**前后端彻底分离**，通过 JSON 接口交互。
- **解决的问题：** 体验提升，前端拥有了独立的控制权。
- **遗留的痛点：** 虽然 DOM 操作被封装，但依然频繁操作 DOM，随着应用变大，代码变得难以维护，容易变成“意大利面条式代码”。

**第三阶段：现代框架与组件化时代 - MVVM**

- **技术栈：** **React, Vue, Angular**，Virtual DOM，Webpack。
- **特征：** 引入了**组件化**思想和**数据驱动视图**（MVVM 模式）。我们不再直接操作 DOM，而是通过修改 State，由框架自动更新视图。工程化工具兴起。
- **解决的问题：** 极大地提升了开发效率和代码可维护性，使得开发超大型应用（单页应用 SPA）成为可能。
- **遗留的痛点：** **首屏加载慢**（需要下载大量 JS）、**SEO 不友好**（爬虫看不到内容）。单页应用变得过于臃肿。

**第四阶段：工程化、全栈化与新时代**

- **技术栈：** **Next.js/Nuxt.js (SSR)**, **TypeScript**, **微前端**, **Serverless**, **Rust 工具链**。
- 特征：
  - **渲染回归：** 为了解决性能和 SEO，SSR（服务端渲染）回归，结合了首屏快和交互好的优点。
  - **类型安全：** TypeScript 成为标配，解决了大型项目协作的类型约束问题。
  - **架构解耦：** 微前端解决了巨石应用问题，允许不同团队独立部署。
  - **性能极致：** 开始使用 Rspack/Turbopack 等 Rust 语言编写的高性能构建工具。
- **解决的问题：** 兼顾了高性能、高可维护性和大规模团队协作。



**3.驱动演进的核心动力**

三个核心驱动力：

> 1. **用户体验 (UX)：** 从‘跳转刷新’到‘无刷新’，再到‘秒开首屏’，始终追求更接近 Native 的体验。
> 2. **业务复杂度：** 从简单的展示页变成复杂的操作系统（SaaS），迫使架构必须从‘过程式’转向‘组件化、模块化’。
> 3. **开发效率：** 为了应对日益复杂的业务，必须通过自动化工具链和抽象框架，让开发者‘做更少的事，产出更多的价值’。



**4.未来展望**

**有最好的架构，只有最适合业务阶段的架构**

> - 对于简单的活动页，传统的 MPA 或轻量级 SSR（如 Nuxt）可能比复杂的 React SPA 更高效。
> - 对于复杂的后台系统，SPA + 微前端是首选。

**关于未来趋势：**
我认为前端架构正在向**‘Server Components’（服务端组件）** 和 **‘AI 辅助开发’** 演进。
React Server Components 允许我们在服务端和客户端之间无缝穿梭组件，进一步减少客户端 JS 体积；
而 AI 正在改变编码方式，未来前端架构师的价值将更多体现在**设计体系、复杂逻辑编排和架构决策**上，而非简单的写页面代码。

## 前端工程化是什么

**按照项目的生命周期来分配：**

- 需求评审：技术选型
- 开发前：统一规范
- 开发中：模块化、组件化
- 开发完：测试
- 编译：构建工具
- 部署：自动化部署
- 上线后：性能监控
- 发现问题：性能优化
- 项目迭代：重构
- 项目巨型化：微服务
- 无服务架构升级：Serverless 

> - **本质**：将软件工程的思想、规范和工具引入前端开发。
> - **目标**：降本增效（提高开发效率、降低维护成本、保证代码质量）。
> - **定位**：它不是单一的工具，而是一个贯穿“开发 -> 构建 -> 测试 -> 部署 -> 监控”的全生命周期体系。

**四大核心维度**

> 1. **模块化**（JS/CSS/资源的模块化管理）：基础，让代码结构清晰。
> 2. **组件化**（UI/逻辑复用）：手段，极大提升了开发效率。
> 3. **规范化**（ESLint/Prettier/Git Commit 规范）：保障，确保了多人协作的质量。
> 4. **自动化**（构建、部署、测试流程自动化）：目标，释放了生产力。

**1.模块化**

> - **JS 模块化：** 我们经历了从 `IIFE`、`AMD/RequireJS`、`CommonJS` 到现在的 `ES6 Modules (ESM)` 的演变。目前通过 `import/export` 配合构建工具，我们可以清晰地管理代码依赖，实现按需加载。 Monorepo（多包管理）处理多项目模块共享。
> - **CSS 模块化：** 为了解决 CSS 全局污染的问题，我通常会使用 CSS Modules、CSS-in-JS（如 styled-components）或者 CSS 预处理器（如 Sass/Less）的嵌套和 `@import` 特性，将样式与组件绑定，实现样式的局部化。
> - **资源模块化：** 在 Webpack 或 Vite 的配置下，图片、字体等非代码资源也被视为模块。我们可以直接在 JS 中 `import` 图片，构建工具会自动处理其引用路径、压缩甚至 Base64 转换，这让资源管理变得更加统一和高效。”

**2.组件化**

> - **UI 组件复用：** 我们会基于基础 UI 库（如 Ant Design 或 Element Plus）进行二次封装，沉淀符合公司设计规范的业务通用组件，比如特定的搜索表单、弹窗组合或复杂表格，避免重复造轮子。
> - **逻辑复用：** 除了 UI，我也很关注逻辑的复用。在 React 中，我会使用 Hooks（如自定义 Hook）抽取公共逻辑（如权限控制、请求封装）；在 Vue 中则会使用 Composables。
> - **组件设计原则：** 我遵循‘高内聚、低耦合’的原则，确保组件通过 Props 传入数据，通过 Events 抛出事件，保持组件的纯净性和独立性，这样无论在哪个页面复用都能保持稳定。比如微前端。

**3.规范化**

> - **代码风格：** 我使用 **ESLint** 配合 **Prettier**。ESLint 负责检查潜在的代码错误（如未使用的变量），Prettier 负责统一格式（如单引号、分号）。两者配合可以彻底解决‘谁写的代码格式不一样’这种争论。
> - **Git 提交规范：** 我们引入了 **Commitlint** 和 **Husky**。在 `pre-commit` 钩子中运行 Lint 检查，在 `commit-msg` 钩子中检查提交信息格式（如 `feat: add new feature`），这保证了代码历史的清晰和可追溯性。
> - **目录结构规范：** 项目通常采用统一的目录结构（如按功能模块划分或按技术类型划分），并制定统一的变量命名和注释规范，让新人能快速上手项目。

**4.自动化**

> - **构建自动化：** 利用 Webpack 或 Vite，自动化完成代码转译（Babel）、压缩、Tree-shaking、代码分割等操作，无需人工干预。
> - **测试自动化：** 引入单元测试框架（如 Jest 或 Vitest），编写核心逻辑的测试用例，并在每次提交时自动运行，防止回归 Bug。
> - **部署自动化（CI/CD）：** 我配置过 GitHub Actions 或 Jenkins 流水线。当代码合并到主分支时，自动触发构建、将产物推送到 CDN/服务器，并自动发送钉钉/飞书通知。整个过程实现了‘一键发布’，极大地降低了上线风险和人力成本。比如低代码。

**其他**

Rust 工具链、Serverless、AI 辅助编程

## 主流构建工具

**速记口诀**

> - **Webpack**：大而全，生态强，先打包后启动，适合大项目维护。
> - **Vite**：快而新，开发爽，利用原生 ESM，生产环境用 Rollup。
> - **Rollup**：小而净，打包库，Tree-shaking 最优，产物体积最小。

| 对比维度         | **Webpack**                                                  | **Vite**                                                     | **Rollup**                                                   |
| :--------------- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **核心定位**     | 功能全面的**应用打包器**                                     | 下一代前端**开发构建工具**                                   | 基于 ESM 的**类库打包器**                                    |
| **开发环境原理** | **先打包，后启动**。 从入口递归分析依赖，编译打包成 Bundle 后再启动服务器。 | **No Bundle (不打包)**。 利用浏览器原生 ESM，按需编译，只编译当前页面用到的文件。 | 主要面向生产环境打包，开发环境支持较弱（通常需配合插件）。   |

| **生态与扩展**   | **生态最强**。 Loader 和 Plugin 极其丰富，能处理任何类型资源（CSS/Img/TS等）。 | **生态新兴**。 兼容 Rollup 插件，社区发展极快，主流框架已全面支持。 | **生态适中**。 插件机制简洁，适合处理纯 JS/TS 逻辑，资源处理需插件支持。 |

| **最佳适用场景** | **复杂的企业级应用**、遗留项目维护、需要极强兼容性的项目。   | **绝大多数新项目**、Vue/React 快速原型开发、追求开发体验的项目。 | **第三方库开发**（如组件库、工具函数库）、框架源码打包。     |

## 组件化_微前端

**1.定义**

“微前端是一种架构风格，它的核心思想是将**巨石前端应用拆解为多个可独立开发、独立部署、独立运行的小型子应用**。
如果说组件化是对 UI 的拆解，那么微前端就是对**应用的拆解**。它主要解决了随着业务复杂度增加，团队协作困难、技术栈无法升级、构建部署缓慢等‘工程化’难题。

**2.核心难点与原理**

前端主要面临三大核心挑战：

> 1. 路由与子应用加载：
>    - 需要有一个**基座应用**，监听路由变化。
>    - 当路由匹配到某个子应用的规则时，动态加载该子应用的资源（JS/CSS），并初始化；当路由离开时，卸载子应用。
> 2. JS 隔离（沙箱机制）：
>    - 为了防止子应用修改全局变量（如 `window`）污染其他应用或基座，需要做沙箱隔离。
>    - 常见的方案有：**快照沙箱**（记录运行前后状态差值，适用于单实例）、**代理沙箱**（使用 ES6 Proxy 拦截操作，目前主流方案）。
> 3. CSS 隔离：
>    - 防止样式互相覆盖。
>    - 常见方案有：**Shadow DOM**（浏览器原生隔离，但兼容性或某些场景受限）、**Scoped CSS**（类似 Vue 的样式 scoped，编译时添加选择器前缀）、**CSS Namespace**（约定前缀）。
> 4. 应用间通信：
>    - 基座与子应用、子应用之间需要数据共享。
>    - 常见方式：**自定义事件**（EventEmitter）、**全局状态管理**（如 Redux 共享 store）、**URL 参数**、**LocalStorage/SessionStorage**。

**3.主流技术方案选型**

> 1. 基于 Single-SPA 的生态（推荐：qiankun）：
>    - **特点：** 阿里开源，基于 Single-SPA 封装，开箱即用。它解决了 HTML Entry（直接解析 HTML 入口文件）、JS 沙箱和样式隔离的问题。
>    - **适用：** 大多数中后台管理系统的微前端改造，技术栈无关性强。
> 2. Webpack Module Federation（模块联邦）：
>    - **特点：** Webpack 5 原生支持。它允许一个应用动态加载另一个应用的代码模块，实现代码的按需加载和共享依赖。
>    - **适用：** 技术栈统一（如都是 React 或 Webpack）的场景，拆分粒度更细，没有额外的沙箱开销。
> 3. iframe 方案：
>    - **特点：** 浏览器原生支持，隔离性最好（JS/CSS 完全隔离）。
>    - **缺点：** 性能差、URL 不同步、弹窗遮罩问题、全屏适应困难。
>    - **适用：** 快期集成老旧第三方页面，对隔离性要求极高且对交互体验要求不高的场景。

**4.实战经验（STAR 法则）**

*这是拿 Offer 的关键，讲述一个真实的改造故事。*

“**背景：** 在我之前负责的**SaaS 运营平台**项目中，随着业务线扩张，单体应用变得非常臃肿，构建一次需要 10 分钟，且不同业务线（订单、营销、用户）分别由不同团队维护，经常出现代码冲突和互相覆盖样式的问题。

**任务：** 我主导了项目的微前端改造，目标是实现各业务线**独立开发、独立部署**，并提升构建速度。

**行动：**

- **基座搭建：** 我选择了 **qiankun** 作为基座框架，搭建了主应用，负责导航栏、权限控制和路由分发。
- **子应用拆分：** 将巨石应用拆分为‘订单中心’、‘营销中心’等 4 个子应用。
- **技术升级：** 允许‘营销中心’的新功能使用 Vue 3 开发，而旧模块保持 Vue 2，通过 qiankun 的 `loadMicroApp` 加载，实现了技术栈的平滑升级。
- **优化处理：** 针对预加载性能问题，我配置了 `prefetch` 策略，在主应用空闲时预加载子应用资源，提升了首屏加载体验。同时设计了全局通信总线，统一处理用户登录态信息。

**结果：** 改造完成后，各业务线构建时间从 10 分钟降低至 **2 分钟**以内，彻底解决了代码冲突问题，新业务线的接入效率提升了 **50%**。

**5.优缺点**

> - 优点：技术栈无关、独立部署、提升团队并行开发效率
> - 缺点：性能略有损耗（需要加载多个运行时）、调试变得复杂（跨应用调试困难）、共享状态管理复杂。

微前端不是银弹，不应为了用而用。它最适合**中大型复杂后台系统**或者**需要整合遗留系统**的场景。在选择方案时，我会优先评估团队技术栈和隔离性需求，如果是 React 技术栈为主且追求性能，我会倾向 Module Federation；如果是异构技术栈整合，qiankun 是更稳妥的选择。

**💡 面试高分小抄（备忘录）**

- Q: qiankun 的沙箱是怎么实现的？
  - A: 在支持 Proxy 的环境下，使用 **Proxy 沙箱**，创建一个假的 `window` 对象代理子应用的读写。在不支持的环境下（如旧浏览器），降级使用 **快照沙箱**，在应用挂载前记录 `window` 状态，卸载时恢复。
- Q: 子应用之间怎么跳转？
  - A: 通常由**主应用**统一管理路由。子应用内部跳转使用 `history.pushState`，并通过全局通信通知主应用更新侧边栏高亮。或者使用 qiankun 提供的 `history` 模式，由主应用接管路由变化。
- Q: 微前端和 Monorepo 的区别？
  - A: Monorepo 是**代码仓库管理策略**，侧重于代码组织和依赖共享；微前端是**应用运行架构**，侧重于页面集成和运行时隔离。两者可以结合使用：代码放在 Monorepo 管理，构建产物作为微前端应用部署。

## 自动化_低代码

**1.定义**

低代码是一种**可视化、模型驱动**的应用开发平台。在前端工程化的范畴里，它是**自动化和平台化**的极致体现。
它的核心思想是：通过可视化拖拽配置 UI，通过编写 JSON 协议描述业务逻辑，再由渲染引擎将其转换为真实的代码运行。本质上，它是在**前端开发之上再做一层抽象**，将‘写代码’降维成‘配置数据’，从而实现非开发人员也能参与构建页面，极大提升研发效率。



**2.核心架构与技术实现**

四个核心部分组成：

> 1. 可视化编辑器：
>    - 这是用户操作的界面。核心难点在于实现拖拽交互，我通常会使用 HTML5 原生 Drag & Drop API 或库（如 `react-dnd`）。
>    - 它包含组件面板、画布和属性配置面板。用户在画布上的操作（增删改查）会实时映射到数据模型上。
> 2. DSL（领域特定语言）/ 描述协议：
>    - 这是低代码平台的**核心灵魂**。我们需要定义一套标准化的 JSON Schema 来描述页面结构。
>    - 比如，描述一个按钮，DSL 可能是：`{ component: 'Button', props: { type: 'primary', text: '提交' }, events: { onClick: 'handleSubmit' } }`。
>    - DSL 的设计决定了平台的扩展能力，通常需要支持组件嵌套、表达式绑定、循环/条件渲染等。
> 3. 渲染引擎：
>    - 负责将 DSL 解析并渲染为真实的视图。
>    - **实现方式：** 一般采用**动态组件加载**技术。在 React 中，可以通过 `componentMap` 映射字符串到真实组件，然后递归渲染 DSL 树。为了性能优化，常配合 `React.memo` 或虚拟滚动。
> 4. 物料系统：
>    - 即组件库。低代码平台必须提供丰富的基础组件（原子组件）和业务组件（分子组件）。
>    - 这里的组件不仅要包含 UI，还需要包含一份 **Setter 配置器**，告诉编辑器这个组件有哪些属性可以配置（如 Input 组件有 placeholder、disabled 等）。

**3.核心难点与解决方案**

主要面临三个挑战：

> 1. 逻辑编排的表达：
>    - 拖拽 UI 容易，但处理复杂逻辑（如接口请求、数据联动）很难。
>    - **方案：** 我会引入**逻辑编排面板**或**表达式引擎**（如 JSON Logic Form）。通过连线的方式定义 `Trigger`（触发器） -> `Action`（动作，如发请求、赋值、弹窗），实现非代码化的逻辑控制。
> 2. 自定义能力的扩展：
>    - 标准组件无法满足所有需求，平台必须有逃生机制。
>    - **方案：** 提供**自定义插槽**或**在线编码**功能，允许用户在特定位置注入原生 JS/Vue/React 代码，保证灵活性不被限制。
> 3. 数据来源与状态管理：
>    - 页面数据从哪来？变量如何维护？
>    - **方案：** 设计一套全局的数据上下文，支持定义变量、接口数据源，并建立数据与组件属性的双向绑定机制。

**4.实战经验（STAR 法则）**

**背景：** 我之前所在的公司的**营销运营团队**，每次搞大促活动都需要开发大量的 H5 落地页。这些页面结构相似（头图、表单、商品列表），但样式多变，开发团队不仅沦为“填题机器”，还经常因为修改文案反复发布。
**任务：** 我主导搭建了一套**营销活动搭建平台**，目标是将运营人员从提需求排期的模式，转变为自助搭建，研发效率提升 80%。
**行动：**

- **DSL 设计：** 设计了一套基于 JSON 的页面描述协议，支持绝对布局和流式布局切换，以适应运营复杂的视觉设计。
- **组件沉淀：** 封装了 20+ 个营销专用组件（如倒计时、抽奖转盘、裂变分享），并为每个组件编写了详细的 Setter 配置面板。
- **逻辑编排：** 针对活动常见的‘提交表单 -> 弹窗提示 -> 跳转’流程，封装了标准的生命周期钩子和动作链，支持运营配置接口地址。
- **出码能力：** 考虑到 SEO 和极端性能需求，我还实现了‘源码导出’功能，将 DSL 编译成标准的 Vue3 项目代码，支持二次开发。
  **结果：** 平台上线后，90% 的常规活动页由运营在 30 分钟内独立完成，前端团队只需维护平台本身和少量高定制活动，研发资源释放出来专注于核心业务迭代。

**5.优缺点**

> - 优点：极致的提效、降低门槛、统一交付标准
> - 缺点：不仅没有消灭复杂度，反而将复杂度转移到了平台开发上；且在处理高交互、复杂算法的场景时，灵活性不如手写代码。

低代码不是要取代前端开发，而是**将前端的能力产品化、服务化**。
未来我认为低代码会与 **AI 结合（AIGC）**，比如通过自然语言描述直接生成 DSL，甚至生成组件代码，这将是前端工程化 2.0 的重要方向。

如果面试官追问，可以这样答：

- Q: 页面 DSL 是存在服务端还是本地？
  - A: 通常存在服务端数据库。渲染时，前端通过 API 获取 JSON，然后动态渲染。为了性能，可以配合 CDN 缓存。
- Q: 如何处理低代码页面的性能？
  - A: 1. 按需加载组件；2. 图片懒加载；3. 产物的代码分割；4. 如果是静态页面，可以预渲染为纯 HTML。
- Q: 拖拽时，为什么有时候位置对不上？
  - A: 这涉及到坐标转换。鼠标事件在屏幕上的坐标需要转换为画布内的相对坐标，特别是在有缩放、滚动条或者嵌套组件的情况下，计算逻辑要非常严谨。可以使用 `getBoundingClientRect` 进行精确计算。

## 自动化_CI/CD

**1.定义**

**CI/CD** 指的是 **Continuous Integration（持续集成）** 和 **Continuous Deployment/Delivery（持续部署/交付）**。
简单来说，它是一套**自动化的流水线**。

**2.核心流程与阶段**

前端 CI/CD 的流水线通常分为三个主要阶段：

> 1. **持续集成（CI 阶段 - 质量把控）：**
>    - **触发：** 开发者 Push 代码或发起 Pull Request (PR) 时触发。
>    - **Lint & Check：** 自动运行 ESLint、Prettier、Stylelint，确保代码风格统一。
>    - **单元测试：** 自动运行 Jest 或 Vitest 测试用例，保证逻辑正确。通常配置 `git hook`，如果测试不通过，禁止合并代码。
>    - **Build（构建）：** 运行 `npm run build`，生成最终的静态资源（HTML/JS/CSS）。这是最耗时的步骤。
> 2. **持续交付/部署（CD 阶段 - 自动化发布）：**
>    - **产物上传：** 将构建生成的 `dist` 目录上传到对象存储（如阿里云 OSS、AWS S3）或文件服务器。
>    - **CDN 刷新：** 触发 CDN 节点的缓存刷新，让用户访问到最新版本。
>    - **服务器部署（如 Node.js 中间层）：** 如果是 SSR 服务，需要通过 SSH 连接到服务器，拉取最新镜像/代码，重启 PM2 或 Docker 容器。
> 3. **通知与反馈：**
>    - 部署成功或失败后，通过钉钉、飞书、Slack 机器人发送消息通知团队。

**3.主流工具与技术选型**

主流的 CI/CD 工具主要分为两类：

**作为前端开发者，我更倾向于使用 GitHub Actions 或 Vercel，因为它们更轻量、更贴合前端生态。**

> 1. **SaaS 服务（推荐）：**
>    - **GitHub Actions：** 我目前最常用的。它与 GitHub 代码仓库深度集成，配置文件（`.yml`）直接放在项目代码中，开箱即用，社区有大量现成的 `actions` 可以复用。
>    - **GitLab CI：** 配合 GitLab 使用，功能强大，适合企业内网自建代码库的场景。
>    - **Vercel / Netlify：** 针对前端优化的平台，甚至不需要写配置文件，只要关联 GitHub 就能自动实现 CI/CD 和预览环境，体验极佳。
> 2. **自托管：**
>    - **Jenkins：** 老牌工具，插件生态极其丰富，但配置复杂（XML 或 Groovy），维护成本高，适合大型传统企业的复杂流水线。

**4.实战经验（STAR 法则）**

**背景：** 在之前的团队中，我们的部署流程非常原始。前端打包完成后，需要手动登录 FTP/SFTP 工具，把 `dist` 文件夹拖拽上传，偶尔还会出现文件遗漏或者覆盖错误，导致线上报错。而且谁在什么时候发了版，完全没有记录。
**任务：** 我负责搭建一套基于 GitHub Actions 的自动化 CI/CD 流水线，实现‘提交即部署’。
**行动：**

- **编写 Workflow：** 创建了 `.github/workflows/deploy.yml`，配置了 `node:16` 环境。
- **缓存优化：** 配置了 `actions/cache` 缓存 `node_modules`，将每次构建时间从 3 分钟缩短到 40 秒。
- **环境管理：** 利用 GitHub 的 `Secrets` 功能管理不同环境的敏感变量（如 API_KEY、OSS 密钥），确保安全性。
- **自动化脚本：** 编写脚本，在构建完成后自动调用阿里云 OSS 的 SDK 上传文件，并自动刷新 CDN 缓存。
  **结果：** 实现了开发人员提交代码到 `main` 分支后，**5 分钟内**自动完成线上环境的更新。彻底消除了手动上传的人为错误，且每次部署都有详细的构建日志可追溯。

**5.优缺点**

> - **回滚策略：** 因为每次构建都有唯一的版本号或 Commit ID，一旦线上出问题，可以一键回滚到上一个版本的构建产物。
> - **灰度发布：** 可以结合 Nginx 或网关配置，通过 CI/CD 部署新版本到一部分服务器，观察无误后再全量发布。
> - **自动化测试：** 将 E2E（端到端测试，如 Cypress/Playwright）接入 CI 流程，确保发布前核心流程（如下单、登录）无故障。

**💡 面试高分小抄（备忘录）**

如果面试官追问细节，可以这样答：

- Q: CI/CD 中如何优化构建速度？
  - A: 1. 缓存 `node_modules`；2. 使用并行构建；3. 使用更快的包管理器（pnpm > yarn > npm）；4. 缓存 Webpack 的构建缓存。
- Q: 如何区分开发环境、测试环境和生产环境？
  - A: 通常通过 **Git 分支** 或 **Workflow 的输入参数** 来触发不同的 Job。例如 `dev` 分支触发部署到测试环境，`main` 分支触发部署到生产环境。环境变量通过 CI 平台的 Secrets 注入。
- Q: 前端部署到 CDN 后，用户还是看到旧版本怎么办？
  - A: 这是缓存问题。构建时文件名必须带 Hash（如 `app.a1b2.js`），HTML 文件不带 Hash。这样更新后 HTML 指向新的 JS 文件，自动绕过缓存。如果没生效，可能需要配置 CDN 的缓存策略或主动刷新缓存。

## dependencies 和 devDependencies

**1.定义**

> **一句话结论**：dependencies 是**运行时**依赖，devDependencies 是**开发/构建时**依赖

**2.核心区别**

| 维度                                                         | dependencies                            | devDependencies                             |
| ------------------------------------------------------------ | --------------------------------------- | ------------------------------------------- |
| 用途                                                         | 项目**运行时**需要                      | 只在**开发/构建**阶段需要                   |
| 典型包                                                       | vue、react、axios、lodash、element-plus | vite、webpack、eslint、typescript、prettier |
| 生产环境 `npm install --production`（或 `NODE_ENV=production`） | ✅ 会安装                                | ❌ 不安装                                    |
| 判断标准                                                     | 打包产物中**包含**它的代码              | 打包产物中**不包含**                        |

**重点**

> - 你项目的 `dependencies` 和 `devDependencies` 在**你自己项目里**都会被安装
> - 区别体现在**你的包被别人安装时**：如果你的项目是个 npm 包，别人 `npm install 你的包` 时，只会自动安装你的 `dependencies`，**不会**安装你的 `devDependencies`
> - 所以：作为库作者，把运行时依赖写进 `devDependencies` 会导致使用者装不到必要的包 → 报错

# 高级

## SPA和MPA

**1.定义**

**SPA (Single Page Application)** 单页应用，是指只有一个 HTML 页面的应用。通过动态重写当前页面与用户交互，而不是从服务器重新加载整个页面。经典的技术栈有 React、Vue 等，利用 **History API** 或 **Hash** 进行路由管理。

**MPA (Multi-Page Application)** 多页应用，是指应用由多个独立的 HTML 页面组成，每次页面跳转都需要浏览器向服务器发起新的请求，返回新的 HTML。这是传统的 Web 模式，如早期的 JSP、PHP 页面，或者现在的企业官网、电商详情页。

**2.核心区别**

有四个维度的本质区别：

> 1. **页面切换与刷新机制：**
>    - **SPA：** 点击路由链接时，**不会刷新页面**。它通过 JS 监听 URL 变化，卸载旧组件、挂载新组件，只更新局部 DOM，体验接近原生 App。
>    - **MPA：** 每次跳转都会**刷新浏览器**，白屏 reloading，会有明显的页面切换感。
> 2. **资源加载与性能：**
>    - **SPA：** 首屏加载较慢（需要加载所有的 JS/CSS 框架和路由），但在首屏之后的操作极其流畅（资源已缓存，只请求数据）。
>    - **MPA：** 首屏加载快（只加载当前页面的资源），但页面跳转时需要重新请求 HTML 和资源，依赖网络环境，体验不连贯。
> 3. **路由管理：**
>    - **SPA：** 使用**前端路由**（Client-side Routing），路由变化由 JS 拦截处理，不经过后端（需配置 Nginx 支持 fallback）。
>    - **MPA：** 使用**后端路由**（Server-side Routing），每个 URL 对应服务器上的一个具体文件路径。
> 4. **SEO (搜索引擎优化)：**
>    - **SPA：** 传统 SPA 对 SEO 不友好。因为源码只有一个空的 `<div id="app"></div>`，内容是 JS 动态渲染的，爬虫难以抓取。（*注：现在通过 SSR（服务端渲染）如 Next.js/Nuxt.js 已解决此问题*）。
>    - **MPA：** 天然 SEO 友好，HTML 内容直接在服务器生成，爬虫能直接解析文本。

**3.优缺点**

| 维度           | SPA (单页应用)                               | MPA (多页应用)                               |
| :------------- | :------------------------------------------- | :------------------------------------------- |
| **用户体验**   | 极佳，无刷新，交互流畅，有转场动画           | 一般，有白屏刷新，交互有割裂感               |
| **首屏速度**   | 较慢（需加载框架包），需 Code Splitting 优化 | 较快（按需加载页面）                         |
| **SEO 支持**   | 较差（需 SSR/预渲染辅助）                    | 极好（原生支持）                             |
| **开发复杂度** | 高（需管理状态、路由、内存泄漏）             | 低（页面间相对独立，逻辑解耦）               |
| **维护成本**   | 前端维护一套代码，后端只提供 API             | 前后端可能耦合（传统模式），或者维护多个页面 |

**4.实战场景与选型（STAR 法则）**

根据业务形态来选型：

**场景一：中后台管理系统**

- **选择：** **SPA**。
- **理由：** 后台系统对 SEO 无要求，但对交互体验要求极高（如表单筛选、Tab 切换、数据可视化）。SPA 一次加载，后续操作无刷新，能极大提升操作员的效率。

**场景二：电商营销活动页/企业官网**

- **选择：** **MPA** 或 **SSR (Next.js/Nuxt)**。
- **理由：** 这类页面需要极高的 SEO 曝光度（让搜索引擎搜到商品），且首屏加载速度直接影响跳出率。如果用传统 SPA，首屏慢且搜不到，得不偿失。如果是复杂的营销页，甚至会使用多页面架构来隔离每个活动的代码，避免单个页面过于臃肿。

**场景三：混合架构（实战进阶）**

- 在**C端大型应用**中，我们通常会结合两者。例如，首页使用 SSR（服务端渲染）保证 SEO 和首屏速度；登录后的用户中心使用 SPA（客户端渲染）保证交互体验。或者结合 **微前端**，将不同业务线拆分为不同的子应用，子应用内部是 SPA，但整体通过基座加载，实现技术栈隔离。

**5.总结**

> - 如果追求**极致的交互体验**和**应用的整体感**，选 **SPA**。
> - 如果追求**SEO**、**首屏极快**或者**内容展示类**网站，选 **MPA** 或 **SSR**。

**未来的趋势：**
界限正在变得模糊。现在的现代框架（如 Next.js、Remix）推崇 **SSR + hydration（注水）** 或 **ISR（增量静态再生）** 模式。这实际上是利用了 MPA 的首屏优势（服务端直出 HTML），结合了 SPA 的交互优势（客户端接管后续交互），是前端工程化在性能与体验上的最佳平衡点。

**💡 面试追问（高分防守）**

- Q: SPA 如何解决首屏加载慢的问题？
  - A: 1. 路由懒加载；2. Tree-shaking 去除无用代码；3. 开启 Gzip/Brotli 压缩；4. 使用 CDN 加速静态资源；5. 预渲染（Prerendering）针对特定路由生成静态 HTML。
- Q: SPA 的前端路由原理是什么？
  - A: 主要有两种模式：
    - **Hash 模式：** 监听 `hashchange` 事件，URL 带 `#`，兼容性好，不美观。
    - **History 模式：** 利用 HTML5 History API (`pushState`, `replaceState`)，监听 `popstate` 事件，URL 美观，但需要后端配合配置 Nginx `try_files`，否则刷新会 404。
- Q: SPA 如何处理内存泄漏？
  - A: 因为页面不刷新，组件卸载时必须手动解绑事件监听器、清除定时器、销毁全局状态订阅，这也是 SPA 相比 MPA 更需要开发者注意的一点。
